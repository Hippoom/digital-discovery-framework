    Integrated Assessment¶

    Purpose¶

    为当前的 Solution Outline（SO）主张收集并综合证据，判断技术路径是否可信、业务能否采用并持续运作、相关风险与控制如何处理，以及是否值得投入下一阶段。IA 可以在 SO 塑形过程中开始，并将证据带回 SO；每项评估发现都应能对应到它所针对的 SO 主张、范围和版本或修订状态。

    SO 描述提出什么 Solution 及其需要；IA 说明现有证据支持什么、尚不能说明什么、需要跟进什么，并形成对下一投资阶段的建议。

    Work¶

    1. 确认评估对象和决策问题¶

    明确本次评估针对的 SO 主张、范围、相关排除项，以及当前考虑的下一投资阶段。SO 不必为开始 IA 而完全冻结，但参与者需要能识别正在评估的主张和状态。

    先问：这次下一步决定需要弄清什么？哪些假设或未知如果不同，会改变对技术路径、业务采用和运作、风险或投入时机的判断？如果 SO 主张本身不够清楚，先把需要澄清的内容反馈给 SO，不在 IA 中代写 Solution。

    2. 选择有决策价值的调查¶

    从当前已有材料和证据开始，按决策影响、不确定性和下一阶段的范围，决定哪些问题需要进一步调查、调查到什么程度，以及由谁提供相应证据。优先选择能影响判断的最小有用调查；不要求每个评估面做同样深度的工作。

    针对每项重要主张或条件，区分已知事实、来源陈述、假设、推断与未知。记录证据来自哪里、实际支持什么、不能说明什么。没有证据时保留为未知，不把“尚无反例”当成支持。

    Conditions & Constraints 作为调查线索¶

    SO 已识别的 Conditions & Constraints 可帮助选择调查方向，但不会自动成为技术要求或必查项。只对关联到具体 SO 主张、且可能影响当前判断的条件，选择最小有用调查；以下是可能关联，不是固定路由：

    SO 条件 可能触发的调查 归属与边界
    Location & Environment 若已说明的地点、设备、网络、隔离或环境条件影响主张，可调查 Client、依赖可达性或部署/运行路径。 用户所在位置不自动意味着本地部署或数据驻留；部署细节只在对当前判断重要时调查。
    Security & Regulatory 若已说明的信息、访问或处理边界影响技术路径，可调查身份访问、数据来源与处理路径的技术可行性。 义务适用性、控制充分性和风险接受归 Risk & Control；技术可行不代表控制充分或合规。
    Availability & Resilience 若 SO 明确哪些行动需继续、可等待、可降级或应停止，可调查依赖和技术路径是否支持这些行为。 业务接管和持续运营归 Operating Viability；不由此推导 SLO、灾备或恢复设计。
    Performance & Scalability 若 SO 已提出响应、处理量、峰值、批次或增长要求，可调查相关数据、计算、平台和依赖路径及最小验证。 不因提到增长就做容量设计；没有业务期望时不自行设定指标。
    成本、期限、资源等通用约束 若已知许可、平台配额或技术窗口直接限制候选路径，可核验相关技术限制。 人员与支持能力归 Operating Viability；成本、资源和时机影响纳入 Investment & Timing。

    3. 评估技术路径与业务运营路径¶

    这两类可行性问题可以并行调查，具体深度依相关 SO 主张和下一阶段决定。

    Technical Viability¶

    判断 SO 所需的能力、信息、集成和关键技术条件是否存在可信的实现路径。按需评估 SO handoff 中所述 User Client(s) 的技术访问路径，以及既有 Client 是否可扩展；可参考 Identity and Access 方法。当部署、运行时、依赖或最低 IT 运维技术路径会影响当前判断时，可参考 Deployment and Operations 方法。若 SO 已提出相关 Archetype 主张，可按需参考 Archetype 技术路径调查提示。记录主要依赖、技术限制、未知，以及能帮助判断的最小验证。不把详细架构、容量设计或实施方案提前写入 IA。

    Operating Viability¶

    判断业务是否有可信路径采用、负责并持续运作 Solution。按相关主张考虑：工作流程与职责是否能衔接；业务、产品或运营责任人及支持能力是否明确；必要的信息、规则或内容由谁维护；是否需要人员培训、变更或采用安排；反馈、度量、例外处理和人工接管是否有可行方向。

    评估足以支撑下一阶段判断的最低业务运营条件，不要求完成详细运营模型。与之相关的证据可说明前提已具备、能够补齐或仍未知。

    4. 综合 Risk & Control¶

    综合 SO 主张及 Technical / Operating Viability 中发现的相关义务、硬边界和风险，判断需要哪些控制、哪些问题尚未解决，以及是否需要有权限的责任方接受残余风险或设置推进条件。义务或重要风险可独立影响建议，不必等两类可行性调查全部结束后才提出。

    IA 说明风险与控制的证据和影响，但不代替授权方接受风险。一个问题只保留一个主要发现归属；对其他评估面的影响用交接说明，避免重复结论。

    5. 综合 Investment & Timing 并形成建议¶

    综合相关价值证据与战略重点、Technical / Operating Viability 发现、风险与控制、资源和依赖、时机、等待成本及过早投入的代价，判断下一阶段的投资理由和条件。Value & Strategic Fit 的证据应在此综合中可见，但不要求作为单独的维度判断；Solution Fit 主要由 SO 负责，IA 只在证据对具体 SO 主张提出疑问时记录发现并反馈给 SO。

    说明建议及理由、面向下一阶段的重要条件和仍未解决的问题。这是 IA 对决策的建议，不是正式的 Go / Defer / No-go 结论，也不代替投资授权或剩余风险接受。

    SO 中提出的 Conditions & Constraints，应按上述调查线索，根据证据进入 Technical Viability、Operating Viability 或 Risk & Control 的主要发现；其资源、依赖或时机影响再纳入 Investment & Timing。无需另设 Readiness 清单：在交接摘要中说明下一阶段前提是否已具备、可补齐或仍不确定，并引用其主要发现。

    SO 发生实质变化时，与相关责任人判断哪些既有发现仍适用、哪些需针对新主张或范围重新评估；不受变化影响的发现无需重做。

    Minimum record and handoff¶

    记录足以帮助授权决策者判断下一投资阶段的内容：

    • 被评估的 SO 主张、范围、相关排除项及可识别的版本或修订状态；
    • 与决策相关的 Technical Viability、Operating Viability、Risk & Control 和 Investment & Timing 发现；各项按需要的深度表达，不要求评分；
    • 关键证据及来源、它支持和不能说明的内容，以及重要假设和未知；
    • 相关 Conditions & Constraints 的影响及其主要评估归属；
    • 下一阶段尚待满足的前提、后续调查或行动、责任人及时间或触发条件；
    • SO 是否需要修改，哪些发现仍适用或需重新检查；
    • 下一阶段投资建议、理由、预期价值/战略依据和重要条件。

    将详细证据工作底稿链接或引用在相应发现下，不必在 IA 中复制完整 Blueprint 或专业调查材料。IA 的输出交给 Investment Decision；授权决策者再记录正式结果、承诺、风险接受和后续交接。
