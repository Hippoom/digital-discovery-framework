    Solution Outline¶

    Purpose¶

    从 Business Opportunity（BO）出发，形成一个或多个可供 Integrated Assessment（IA）评估的 Solution 主张。SO 说明希望解决什么问题、面向什么用户和场景，以及 Solution 如何改善场景表现；详细实施设计留给后续工作。

    Work¶

    1. 对齐 Solution Vision¶

    从 BO 的背景、目标结果和已知边界出发，收集并对齐相关参与者对 Solution 方向的初步预期。使用 Solution Vision 的 Elevator Pitch 结构表达愿景，帮助不同团队或参与者讨论方向、发现分歧。

    Solution Vision 是共同塑造的方向，不要求精确或完整。提出者带来的 App、报表、AI 或 Agent 等想法可以作为讨论线索，再结合 BO 判断它们是否回应了机会。

    2. 描绘 Solution 如何改善场景表现¶

    依据 Solution Vision，并结合 BO 提供的背景与优先级，选择值得探索的场景。理解相关 User、Touchpoint 和 Action 如何构成场景中的问题或机会，以及 Solution 如何介入并改善表现。

    按需使用场景分析方法，理解当前场景、定位值得改善之处，并形成 Solution 如何改变场景表现的主张。回到 Solution 主张时，识别支持相关 User 行动的 User Client(s) 方向，并说明与相关 Touchpoint 的关系；随着 Location & Environment 等已识别条件明确，再检查该方向是否需要修正。Service Blueprint 的经典元素可作组织场景信息的参考，不要求绘制完整 Blueprint。

    记录应能识别相关 User 与 User Client(s) 方向；若方向尚未明确，标为候选或未定。Touchpoint、Action 和 Scope 只需达到足以理解主张的粒度；仅在具体细节会实质影响主张或技术路径时再展开。

    理解关键用户、分析问题机制和选择 Solution Archetype 是相互支持的视角，不是固定顺序或必做步骤：User Persona 可帮助理解用户的目标和限制；问题与机会分析视角可帮助解释场景中的摩擦；Solution Archetypes 参考可启发回应这些问题的业务主形态。只有在有助于澄清或比较主张时才使用，不要求每个 SO 都指定一种 Archetype。 如果方向之间在业务责任、预期结果、行动边界或范围上存在实质差异，应分别形成 SO 主张，并关联到同一个来源 BO。对同一主张的场景补充不必自动拆成多个 SO。

    3. 探索 Conditions & Constraints¶

    围绕正在形成的 Solution 主张，识别可能影响它的条件与约束，例如业务规则、信息要求、责任边界、适用义务、工作地点或环境因素。可按需使用Conditions & Constraints 发现启发帮助讨论；这些提示不是穷尽清单，也不是每个 SO 都要逐项检查。

    SO 记录与主张相关的条件、来源和仍未明确之处。IA 根据证据评估它们对 Solution 的影响，并决定需要的调查和跟进。

    4. 勾勒演进设想¶

    围绕当前优先考虑的 horizon，按方向性顺序描述后续可能扩展的价值、能力或覆盖范围。记录可能改变顺序、范围或是否继续的假设、依赖与条件；如暂时没有有意义的后续设想，可以只记录当前 horizon。

    Ambition Roadmap 表达 Solution 可能如何演进，不是交付计划、精确排期、资源或成本承诺，也不表示未来范围已获批准。具体投入与是否推进下一 horizon，由 IA 提供评估，Investment Decision 作出决定。

    Minimum record and handoff¶

    SO 的记录可以由多个相互关联的材料组成。它们共同支持团队继续塑造 Solution 主张，并让 IA 开始评估。记录中应能看清：

    • Solution Vision 及其关联的 Business Opportunity；
    • 与 Solution 主张相关的场景及改善设想；可关联场景分析产出（如有）；
    • 相关 User 与 User Client(s) 方向；若方向尚未明确，标注候选或未定。说明与相关 Touchpoint 的关系；Touchpoint、Action、Scope 仅在其细节会实质影响主张或技术路径时补充；
    • 与主张相关的条件与约束，以及 Solution 需要的支持和仍未明确的事项；标明可能改变 User Client(s) 方向或技术路径的已识别 Conditions（如 Location & Environment）；
    • 当前优先考虑的 horizon；如有有意义的后续 horizon，按方向性顺序记录其增量，以及可能改变顺序、范围或是否继续的假设、依赖与条件。无需给出精确日期或资源/成本承诺。

    进入 IA 评估时，双方应能识别当前讨论或评估的 Solution 主张和范围。SO 可以在塑形过程中持续调整；如主张有重要变化，告知 IA 变化内容，以便共同判断是否需要重新检查相关评估。
