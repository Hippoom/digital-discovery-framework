    Under What Conditions¶

    用途：针对一份版本稳定的 Solution Outline，筛选哪些 Quality Concerns 与 Constraints 会实质影响方案，并决定何时需要进一步评估 Workload / Resource Envelope，以及哪些未关闭事项需要汇入 solution-wide RAIDs。

    它不是新的 Technology Assessment Domain、DFX Perspective、Assessment line、生命周期对象或 Gate。它选择和协调后续工作，但不替代各 Domain、Readiness to Proceed、Risk & Control、Investment & Timing 或 Gate 的结论与责任。

    1. 在框架中的位置¶

    Solution Outline
  = What

Technology Assessment Domains
  = With what

  = 哪些 Quality Concerns 与 Constraints
    会实质影响方案；在何种规模/资源包络下需要进一步取证

Integrated Assessment
  = 形成跨线判断

Solution-wide RAIDs
  = 跟踪未关闭且跨域/跨线/Gate 影响的事项

    筛选对象必须能追溯到：

    Outline claim / version / scope
→ target scenario, Actor, action boundary
→ design assumptions and hard constraints
→ Stakeholder Concern
→ existing assessment-domain findings (if any)

    2. 边界与状态词¶

    本模型做什么¶

    • 识别哪些 Quality Concerns 与 Constraints 对当前 Outline 实质相关；
    • 决定应启动哪些 Assessment Domain、评估线或最小证据活动；
    • 在适用时形成方向性的 Workload Profile 与 Resource Envelope；
    • 将未关闭且有跨域、跨线或 Gate 影响的事项汇入 solution-wide RAID register。

    本模型不做什么¶

    • 不重写 Solution Outline 或替代其需求、行动边界与硬约束；
    • 不替代各 Domain 的 Supported / Conditional / Unproven / Blocked 判断；
    • 不生成完整 NFR、SLO/SLA、容量模型、成本模型、拓扑、部署、Runbook 或完整运营设计；
    • 不裁定合规接受性、控制充分性、资源获批或最终投资时机；
    • 不从 L1 Archetype 预填静态的 Readiness / Risk checklist。Archetype 指引可以提出机制或调查提示，但 materiality 必须由具体 Outline claim、Stakeholder Concern、Constraint、范围和触发条件决定。
    记录对象 使用词汇 含义
    条件敏感度筛选 Applicable / Conditionally Applicable / Not Material / Unknown 此 Concern 或 Constraint 是否需要实质影响当前 Discovery 判断。
    Assessment Domain Supported / Conditional / Unproven / Blocked 具体技术路径是否有证据支持。
    证据 E0–E4 当前证据强度。
    未关闭方案级事项 Assumption / Issue / Risk / Dependency 需要持续治理的跨域、跨线或 Gate 事项。

    Applicable 不等于条件已经满足；Not Material 不等于风险已经接受；Unknown 不能因缺少事实而写成 Not Material。

    3. Quality Concerns 与 Constraints 的敏感度筛选¶

    3.1 筛选记录¶

    每条筛选记录至少包含：

    字段 要记录什么
    关联 Outline 主张 / 场景 受影响的目标动作、Actor、行动边界或方案需求。
    Stakeholder Concern / Constraint 谁关心什么，或什么不可协商边界限制路径。
    类别 Quality Concern / Constraint / Other Concern。
    敏感度结果 Applicable / Conditionally Applicable / Not Material / Unknown。
    依据与证据 已知事实、假设、推断与 E0–E4。
    触发 / 复审条件 何时需要重新筛选，例如范围扩展、实时化、跨区域、关键窗口、依赖选择或行动档位变化。
    所需 Assessment / 路由 需要启动的 Domain、Technical Viability、Readiness to Proceed、Risk & Control、Investment & Timing 或 Inception 工作。
    Workload / Resource materiality 是否需要进一步形成 Workload Profile 或 Resource Envelope。
    RAID 候选 未关闭事项是否达到 solution-wide RAID 登记门槛。

    3.2 敏感度结果规则¶

    结果 使用条件 后续动作
    Applicable 已知会实质影响目标动作、技术路径、行动边界、Gate 或交接。 启动必要 Domain / Assessment。
    Conditionally Applicable 仅在范围扩展、实时化、跨区域、关键窗口、依赖选择或行动档位变化时变得实质。 记录触发条件、最小验证与复审时点。
    Not Material 有正向范围证据，证明不会改变当前 Outline 的技术、Gate 或交接判断。 记录范围理由与复审触发；不展开专项。
    Unknown 尚不能判断是否实质。 形成最小 E1/E2 取证，获取证据后重新筛选。

    3.3 非强制的 Quality Concern 起点¶

    以下仅是高频检查起点，不构成每份方案的必填目录：

    • Performance & Scalability；
    • Availability & Resilience；
    • Evolution；
    • Security；
    • Regulatory；
    • Location；
    • Usability；
    • Testability；
    • Observability；
    • 其他由具体 Stakeholder Concern 引出的质量关注。

    3.4 Constraints 起点¶

    Constraints 与 Quality Concerns 并列作为筛选输入，典型包括：

    • 合规、隐私、审计、数据地点、保留期；
    • 固定时间窗口、批处理截止点、季节性或业务上线窗口；
    • 预算、成本、许可、供应商配额或资源上限；
    • 既有平台、供应商、系统、组织、支持模型、采购或变更限制；
    • 已有行动边界、审批、确认与人工接管要求。

    Constraint 可以触发支撑 Technical Viability 的技术事实调查，但其可获得性、控制充分性、可接受性和预算/时机判断仍应路由至 Readiness to Proceed、Risk & Control 或 Investment & Timing。

    4. 从敏感度到 DFX 与 Assessment 选择¶

    Outline claim + Stakeholder Concern / Constraint
  ↓
Under What Conditions sensitivity screening
  ↓
Applicable / triggered Conditional concern
  ↓
choose minimum relevant DFX Viewpoint / View / Perspective
  ↓
relevant Technology Assessment Domain and assessment-line routing
    • DFX Perspective 始终由 Stakeholder Concern 触发；本模型不能将 Perspective 转为所有方案的强制目录。
    • Unknown 只触发最小证据活动，不要求提前建立全套架构 View。
    • 同一事项可以影响多条评估线，但必须指定一个主归属，其余作为交接。
    • Operational 仍是 Viewpoint；Testability / Observability 默认是 Concern 或能力要求，而不是自动独立的 Perspective。

    DFX 术语与最小选择规则见 DFX 在 Digital Discovery 中的最小映射。

    5. Workload Profile 与 Resource Envelope（仅在 material 时）¶

    当 Performance & Scalability、关键成本/配额、批处理窗口、并发、关键时效或运行资源可能改变当前 Gate 判断时，才展开以下轻量调查。

    Workload Profile¶

    记录方向性事实，不形成容量设计：

    • 交互、事件、查询、作业、批次或发布活动类型；
    • 峰值、并发、批处理窗口、周期性与增长方向；
    • 同步 / 异步特征与关键 Actor / 系统路径；
    • 哪些失败、延迟或积压会影响目标动作；
    • 已知的降级、延迟处理、人工接管或停止边界。

    Resource Envelope¶

    记录方向性资源边界，不形成资源 sizing 或报价：

    • 候选平台、运行时、供应商或环境的配额、支持和资源边界；
    • 已知预算、许可、算力、外部调用、存储、网络、人员支持与变更窗口约束；
    • 可能需要资源扩展、采购、批准或替代路径的条件；
    • 资源 Unknown 对 Go / Defer / Inception 的影响。

    本阶段禁止形成精确吞吐/容量、服务器/集群规格、SLO/SLA、资源 sizing、成本报价/模型、拓扑、扩缩容、网络/DR/监控/运行手册设计。

    输出是：负载/资源假设、对当前 Gate 是否 material、最小证据与 Technical Viability / Readiness to Proceed / Investment & Timing 路由。

    6. Solution-wide RAIDs 合成纪律¶

    各 Domain 和 Assessment 线先保留其详细 Findings、证据与状态。仅当事项具有方案级影响时，才汇入 解决方案级 RAID 登记册。

    登记门槛¶

    事项至少符合以下一项时，才进入 solution-wide RAID：

    • 跨多个 Technology Assessment Domain；
    • 跨 Technical Viability、Readiness to Proceed、Risk & Control 或 Investment & Timing 多条评估线；
    • 影响多个 Outline claim，或影响整体行动边界；
    • 可能改变 Go / Defer / No-go、实施切片、投入时机或关键交接；
    • 需要统一 Owner、关闭条件和跨域协调节奏。

    分流规则¶

    事项性质 RAID 类型 主路由
    未验证但必须成立的前提 Assumption 对应 Assessment line / Owner
    已存在、正在阻塞推进的事实问题 Issue 对应 Assessment line / Owner
    可能发生且需要缓解的负面后果 Risk Risk & Control 或对应主线
    外部平台、团队、资源、决策或环境前提 Dependency Readiness to Proceed / Investment & Timing 或对应主线

    RAID 只保留源记录引用、方案级影响、主归属、Owner、关闭证据/决策和 Gate 后果；不复制原 Domain 的详细事实。

    Inception handoff 不等于“未关闭 RAID”。进入 Inception 的事项必须说明为何可在 Go 后深化、需要保留哪些约束及验证证据；未满足 Go 条件的事项仍应保留为 Gate 条件或 RAID。

    7. 与 Integrated Assessment 的接口¶

    • Under What Conditions 的筛选结果进入 综合评估记录卡 的方案级筛选区；
    • 已触发的 Quality Concern 进入对应 Technology Assessment Domain 或 Cross-cutting Quality 记录；
    • 约束按主归属进入 Technical Viability、Readiness to Proceed、Risk & Control、Investment & Timing 或 Inception；
    • RAIDs 仅汇总未关闭且有方案级影响的事项；
    • Gate 使用 Go 前条件、Defer / 重启条件、No-go 理由 和 进入 Inception 的交接 汇集既有判断，而不生成第三份重复方案。

    一句话¶

    Under What Conditions 不假定每个方案都必须满足同一组质量或资源要求；它针对特定 Outline 筛选真正会改变路径、条件、规模、风险和 Gate 的 Concerns 与 Constraints，并将未关闭的方案级事项收敛为可治理的 RAIDs。
