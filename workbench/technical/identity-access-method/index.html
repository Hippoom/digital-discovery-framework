    Identity 与 Access 技术使能¶

    用途：作为 Technology Assessment 下的早期可复用 Assessment Domain，评估 Solution Outline 中的 Target Actor 是否能通过所主张的 Access Modality，以可信的身份、认证和授权判断基础访问目标能力与业务上下文。

    1. 评估对象与边界¶

    Target Actor
  → Identity Source & Resolution
  → Authentication
  → Access Modality / Client Delivery Model
  → Authorization Context & Decision Basis
  → Identity & Access Enablement
    概念 在本专项中的作用
    Target Actor 需要访问、使用或接收结果的内部角色、外部用户或下游系统。
    Touchpoint Context Actor 在何种工作时刻、为获得、提交、确认或升级何种结果而进入交互；只提供调查上下文。
    Access Modality Assumption Actor 通过何种 Channel / Platform / Client Form 进入该 Touchpoint 的方案主张。
    Authorization Context & Decision Basis 系统可用来判断功能访问与数据/上下文范围的 Role、Claim、组织、团队、租户、客户归属、案件责任、任务分派或其他业务关系。

    Touchpoint 本身不接受技术可行性判断。它由业务/SA 在 Solution Outline 中定义；技术只核验 Target Actor 是否能以可信身份、认证和授权判断基础，经由所提出的 Access Modality 到达该 Touchpoint 并获得规定范围的访问。

    Access Modality 是 Channel / Platform 与 Client Form 的上位术语：

    Access Modality
├─ Channel / Platform
│  例如：既有业务系统、企业协作平台、Web、Mobile、API
└─ Client Delivery Model
   ├─ Existing Client Reuse
   ├─ Existing Client Extension
   ├─ Platform-hosted Client
   ├─ Standalone Client
   └─ System-to-system Access
    • Existing Client Reuse：既有 Client 无需实质新增交互能力，即可承载所需访问与交互。
    • Existing Client Extension：既有 Client 可以承载，但需要新增模块、页面、插件、入口或交互能力。
    • Platform-hosted Client：在既有 Channel / Platform 上新建应用、嵌入式 Client、Mini Program、Bot 或类似形态。
    • Standalone Client：新建独立 Web、Mobile 或 Desktop Client。
    • System-to-system Access：由下游系统、服务或自动化流程经 API、事件或服务间路径访问，不经人工 Client。

    本专项不选择最终 Client、产品界面、具体 Role 配置、权限策略语言、IAM 架构或详细访问控制实现；也不判断控制是否足以满足合规或残余风险是否可接受。

    2. 评估域的开发方法与原则¶

    本专项是一个可复用的 Technology Assessment Domain，不是新的核心对象，也不自动等同于 DFX 的 Viewpoint 或 Perspective。后续新增或修订任何评估域时，先按以下五项完成条件开发，再写入调查问题或模板字段。

    完成条件 在本专项中的落实
    明确评估对象 特定 Target Actor 在所主张 Access Modality 下的身份、认证和授权判断基础路径。
    可控评估深度 只判断可信路径、判断依据与关键限制；不设计 IAM 架构、Role 配置、权限策略语言或详细 enforcement。
    可解释的判断逻辑与结果 以三个判断面和 Supported / Conditional / Unproven / Blocked 表达，不使用平均分。
    明确证据与追溯方式 每项判断关联 Outline claim、Stakeholder、Concern、E0–E4 证据、限制与最小验证。
    明确决策接口与主归属 Technical Viability 判断技术路径；本专项识别条件并通过 Under What Conditions 路由；Readiness to Proceed 判断前提可获得性；Risk & Control 判断控制与风险接受；Inception 深化实现。

    开发节奏¶

    1. 从 Solution Outline 提取待评估主张与边界
2. 明确 Stakeholder Concern 和评估对象
3. 定义最少且相互不重叠的判断面
4. 为每个判断面定义调查问题、事实类型与最小证据
5. 定义 Supported / Conditional / Unproven / Blocked 的判定逻辑
6. 明确 Readiness to Proceed、Risk & Control、Inception 的主归属与交接
7. 使用真实或历史场景回填；发现无法表达的 Concern 时再修订本专项

    通用纪律¶

    • 证据先于结论：事实、假设、推断、条件与结论分开记录；E0–E4 表示证据强度，不替代判断状态。
    • 不从技术分类倒推问题：先有 Outline claim 与 Concern，再选择调查问题和 DFX 语言。
    • 不以评估域替代 Solution Outline：评估域不重新定义 Actor、Touchpoint、Access Modality 或访问范围主张。
    • 不把跨线事项留在技术结论中：前提可获得性、控制充分性和风险接受性必须交给相应 Assessment 线形成主结论。
    • 以最小充分深度止步：只取足以支持 Go / Defer / No-go 或 Inception 交接的证据；详细设计下沉。

    3. Solution Outline 输入¶

    输入 要求
    Target Actor 谁需要访问；其角色、组织边界及与目标动作相关的工作身份。
    Touchpoint Context Actor 在何种工作时刻，需要获得、提交、确认或升级什么。
    Access Modality Assumption 首选的 Channel / Platform 与 Client Delivery Model；必要时说明可接受的替代形态。
    必要工作上下文 进入时需要携带或重建的角色、组织、客户/账户、任务/案件、业务对象或状态上下文。
    所需访问判断粒度 对新能力和业务范围，是否需要按角色、组织、团队、租户、客户、案件、任务或其他关系区分。

    Outline 只写“需要 / 应具备 / 必须遵守”的主张，不写“平台已支持”“身份已接通”“Role 已配置”或“访问控制已满足合规”等 Assessment 结论。

    4. 技术调查问题¶

    3.1 Identity & Authentication Enablement¶

    调查问题 需要收集的技术事实
    Target Actor 是否存在权威身份来源，技术身份能否关联业务身份？ 身份域、账号来源、身份映射、组织/团队/岗位等身份属性的来源。
    候选 Access Modality 是否能使用既有 IdP、SSO、Federation 或其他受支持机制完成认证？ 认证协议、会话、token、system-to-system credential、平台支持路径与限制。
    跨 Client 或系统时，认证与必要身份上下文能否延续或安全重建？ 跳转、深链、回跳、会话、身份映射、上下文传递的技术路径与限制。
    是否会产生额外注册、独立账号、人工绑定或非受管身份？ 例外身份路径、重复身份与不可管理身份的技术影响。

    3.2 Access Modality & Client Delivery Enablement¶

    调查问题 需要收集的技术事实
    Target Actor 当前可使用哪些既有 Channel / Platform？ 已部署且实际可用的平台、客户端与入口。
    哪种 Client Delivery Model 可能承载该 Assumption？ Existing Client Reuse、Existing Client Extension、Platform-hosted Client、Standalone Client 或 System-to-system Access 的候选路径。
    Candidate Platform 是否支持该 Client Delivery Model？ 支持的复用、扩展、嵌入、应用、Web 交付、API 访问或其他受支持路径。
    该形态能否承载该 Touchpoint 所需的最低交互？ 必需交互的技术承载能力与明确限制；不重新定义 Touchpoint。
    是否存在受支持的交付、升级、替换或退出路径？ 技术交付与生命周期路径；平台 Owner、资格和资源准备交给 Readiness to Proceed。
    若首选 Assumption 不成立，是否存在可接受的替代路径？ 可替代的 Channel / Platform / Client Delivery Model 及其技术影响。

    3.3 Authorization Context & Decision Basis¶

    本节不定义“谁最终拥有什么权限”，而是评估是否已有或可建立足够的依据和机制，使系统能对功能访问与数据/上下文范围作出授权判断。

    调查问题 需要收集的技术事实
    是否存在可供候选 Client / Platform / Service 使用的 Role、Claim、Entitlement 或等效机制？ 当前功能访问判断机制、可用身份属性、传递和使用路径。
    现有机制的粒度是否足以区分新能力的访问需要？ Role / Claim / Entitlement 的粒度、封闭性、可复用性与已知限制。
    新能力可复用现有机制，还是需要扩展或新建判断基础？ 角色扩展、Claim 增加、映射关系、独立 entitlement mechanism 的可行性假设。
    是否存在可靠依据判断数据/业务上下文范围？ 组织、团队、租户、客户归属、案件责任、任务分派、区域或其他业务关系的权威来源。
    这些依据能否在目标 Client / Platform / Service 被取得并用于判断？ 身份属性、业务关系、上下文传递与使用的技术路径。
    当前粒度是否足够？ 例如只有部门信息，但 Outline 需要区分到客户、案件、任务或业务对象范围。

    Access control execution path 是本节的横向检查：已有身份、角色、范围或关系依据，是否能在实际 Client、Service、API 或目标系统的访问边界被使用和执行。Discovery 只判断是否存在可信路径，不设计详细 enforcement architecture。

    3.4 证据、限制与交接¶

    • 哪些限制会迫使 Solution Outline 修改 Access Modality Assumption 或访问范围主张？
    • 哪些假设可由 E1 平台资料、身份/Role 模型和系统说明核验，哪些需要 E2 样本核验，哪些需要 E3 Spike？
    • 哪些发现应交给 Readiness to Proceed（如平台 Owner、发布路径、身份源、授权协作、属性或关系来源协作）？
    • 哪些发现应交给 Risk & Control（如最小权限、职责分离、敏感数据暴露、审计、强认证或访问例外）？

    5. 结构化评价¶

    不使用打分或平均分。每个判断面分别记录状态、证据、条件和交接，再按关键路径形成专项结论。

    判断面 要评价什么
    Identity & Authentication Enablement Target Actor 是否有可管理的身份来源与业务身份关联路径；候选 Access Modality 是否能以受支持机制完成认证并维持必要身份上下文。
    Access Modality & Client Delivery Enablement 所主张的 Channel / Platform / Client Delivery Model 是否存在受支持的承载、交付、升级和替代路径。
    Authorization Context & Decision Basis 是否存在、可取得且粒度足够的 Role、Claim、组织/团队、业务关系或等效机制，为功能访问与数据/上下文范围作出授权判断；这些依据是否有可信 execution path。

    每个判断面及专项结论均采用：

    状态 含义
    Supported 已有证据支持该技术主张。
    Conditional 技术路径存在，但依赖明确条件或仍需补充有限证据。
    Unproven 尚无足够证据，不能据此形成可行性结论。
    Blocked 已知限制否定该主张，或必须修改 Outline / 采用替代路径。

    E0–E4 记录“凭什么知道”，不等同于上述判断状态。

    专项结论规则¶

    任一关键判断面 = Blocked
→ 专项通常为 Blocked；除非修改 Outline 主张或采用替代路径。

无 Blocked，但存在关键 Unproven
→ 专项为 Unproven；应优先补证据，不称为“有条件可行”。

关键路径均已验证，但存在外部条件
→ 专项为 Conditional；识别条件并通过 Under What Conditions 路由至 Readiness to Proceed / Risk & Control / Investment & Timing / Inception。

全部关键判断面均为 Supported
→ 专项为 Supported。

    使用 综合评估记录卡 记录每项判断面与专项结论，并关联具体 Outline claim、Stakeholder、Concern、Viewpoint / 最小 View、E0–E4 证据、条件和交接。

    6. 主归属¶

    内容 主归属
    Target Actor、Touchpoint、Access Modality Assumption、所需访问范围 Solution Outline
    身份、认证、授权判断基础、平台、Client Delivery Model 与可信 execution path 是否存在 Technical Viability
    平台 Owner、发布资格、资源、身份源、属性/业务关系来源与协作是否可获得 Readiness to Proceed
    最小权限、职责分离、敏感数据暴露、审计、强认证、访问例外与残余风险是否可接受 Risk & Control
    Client 的详细 UX、最终产品形态、IAM / policy / enforcement 架构与发布设计 Inception / Implementation

    一句话¶

    Identity & Access Enablement 不评估 Touchpoint 是否合理，也不配置具体权限；它评估 Target Actor 是否存在可信的身份、认证、授权判断基础和 Access Modality 路径，足以在所主张的功能与业务范围内获得访问。
