    Knowledge & Expert Assistance — Information 与 Knowledge 技术使能¶

    路径：Knowledge & Expert Assistance Realization → Archetype Realization。

    用途：作为 L1 Knowledge & Expert Assistance 下当前唯一已实现的 specialised Technology Assessment item，评估该 Archetype 所主张的信息、知识、规则、业务对象、状态与证据，是否存在可信的技术可用路径，并能否以足够可信的内容支撑专业解释、指导、校验或升级等目标用途。

    本专项的两个局部技术判断面是 evidence structure，不是通用 Archetype 的第三层，也不为本 Archetype 或其他 Archetype 创建固定的 Readiness to Proceed / Risk checklist 或 Solution Operating Model。

    1. 评估对象与边界¶

    Solution Outline
  → Initial Information Requirements
  → Information Requirement Elaboration
  → Information Availability & Contextual Use
  → Information Trustworthiness & Fitness for Intended Use
  → Information & Knowledge Enablement
    概念 在本专项中的作用
    Initial Information Requirements Outline 初步提出的、为目标动作所需的关键类别：信息、知识、规则、业务对象、状态与证据。
    Information Requirement Elaboration 将初步需求拆到足以判断来源、技术可用性与可信可用性的粒度；是 Assessment 的工作过程，不是新核心对象或完整数据建模。
    Usage Context 由谁、在何种 Touchpoint Context、为解释、判断、确认或行动的哪一步使用。
    Information Access Mechanism 从源系统、知识源、规则源、事件或记录来源取得、关联、过滤、引用或回写所需内容的技术路径。

    本专项不判断信息需求是否合理，也不选择数据平台、知识库、RAG、模型、检索策略、数据管道或详细集成架构。它只核验：针对 Outline 已提出的需求，是否存在可取得、可关联、可按访问范围使用且足以支撑目标用途的信息与知识路径。

    2. 评估域的开发方法与原则¶

    本专项是一个可复用的 Technology Assessment Domain，不是新的核心对象，也不自动等同于 DFX 的 Viewpoint 或 Perspective。后续新增或修订任何评估域时，先按以下五项完成条件开发，再写入调查问题或模板字段。

    完成条件 在本专项中的落实
    明确评估对象 L1 Knowledge & Expert Assistance 主张所需的信息、知识、规则、业务对象、状态与证据的技术可用性与可信可用性。
    可控评估深度 只判断信息需求能否取得、关联、按范围使用并支撑目标用途；不设计数据平台、知识库、RAG、数据管道、数据治理或详细接口。
    可解释的判断逻辑与结果 以两个判断面和 Supported / Conditional / Unproven / Blocked 表达，不使用平均分。
    明确证据与追溯方式 每项判断关联 Outline claim、Stakeholder、Concern、E0–E4 证据、限制与最小验证。
    明确决策接口与主归属 Technology 判断技术路径并识别条件；是否 material 由 Under What Conditions 筛选；Readiness to Proceed 判断 Owner、授权与维护前提；Risk & Control 判断数据使用与合规风险接受；Inception 深化实现。

    开发节奏¶

    1. 从 Solution Outline 提取初步信息需求与边界
2. 将需求拆到足以调查的粒度（Information Requirement Elaboration）
3. 明确 Stakeholder Concern 和评估对象
4. 定义最少且相互不重叠的判断面
5. 为每个判断面定义调查问题、事实类型与最小证据
6. 定义 Supported / Conditional / Unproven / Blocked 的判定逻辑
7. 明确 Readiness to Proceed、Risk & Control、Inception 的主归属与交接
8. 使用真实或历史场景回填；发现无法表达的 Concern 时再修订本专项

    通用纪律¶

    • 证据先于结论：事实、假设、推断、条件与结论分开记录；E0–E4 表示证据强度，不替代判断状态。
    • 不从技术分类倒推问题：先有 Outline claim 与 Concern，再选择调查问题和 DFX 语言。
    • 不以评估域替代 Solution Outline：评估域不重新定义信息、知识、规则、业务对象或状态需求。
    • 不把跨线事项留在技术结论中：本专项可识别条件和提供技术证据；其 materiality 先由 Under What Conditions 筛选，Technology、Readiness to Proceed、Risk & Control 和 Gate 效果由 Integrated Assessment 形成跨线判断。Owner、授权、维护、数据使用边界和风险接受性必须交给相应 Assessment 线形成主结论。
    • 以最小充分深度止步：只取足以支持 Go / Defer / No-go 或 Inception 交接的证据；详细设计下沉。

    3. Solution Outline 输入¶

    输入 要求
    Initial Information Requirements 需要哪些信息、知识、规则、约束和证据，分别支持什么目标动作或行动边界。
    Business Object / State 涉及哪些业务对象、状态、事件、任务/案件或记录；需要读取、理解、关联还是更新。
    Usage Context 由谁、在何种 Touchpoint Context、为解释、判断、确认或行动的哪一步使用。
    Timeliness / Traceability Need 对时效、版本、来源、证据引用、历史状态或可追溯性的方向性要求。
    Access Scope Assumption 信息/知识使用是否需要按组织、团队、客户、案件、任务、租户或其他业务关系区分范围。

    Outline 只写“需要 / 应具备 / 必须遵守”的主张，不写“数据已可用”“知识质量足够”“接口已开放”或“可以合规使用”等 Assessment 结论。

    4. Assessment 工作过程：Information Requirement Elaboration¶

    Outline 的初步信息需求可以是“当前客户事实”“适用政策”“案件状态”等类别。Assessment 将其拆至足以进行技术核验的粒度，但不扩展为完整数据模型或数据治理设计。

    Initial requirement
= 当前客户事实与适用政策

Elaborated requirement set
= 客户身份与归属
+ 当前合同 / 服务状态
+ 当前案件、任务与历史处理记录
+ 已生效政策文本与版本
+ 适用条件、例外与引用依据

    每个被展开的需求应至少说明：

    • 它支撑哪条 Outline claim、目标动作或行动边界；
    • 需要什么业务对象、状态、规则、知识或证据；
    • 预期使用情境、时效和可追溯性要求；
    • 需要何种访问范围或业务关系上下文。

    5. 结构化评价¶

    不使用打分或平均分。每个判断面分别记录状态、证据、条件和交接，再按关键路径形成专项结论。

    判断面 要评价什么
    Information Availability & Contextual Use 已展开的信息需求是否存在可行的技术路径，以取得、查询、订阅、关联、过滤、引用或必要时回写内容，并带入正确的业务对象、状态和使用上下文。它应利用 Identity & Access Enablement 已评估的身份、认证与授权判断基础，判断信息访问机制能否按 Actor 的功能与数据范围执行。
    Information Trustworthiness & Fitness for Intended Use 已取得的信息、知识、规则、状态与证据是否能被合理识别为可信来源，并在 Authority、Provenance、Currency、完整性/一致性、版本和引用依据方面，足以支撑该 Outline 的预期解释、判断、确认或行动。

    判断状态¶

    每个判断面及专项结论均采用：

    状态 含义
    Supported 已有证据支持该技术主张。
    Conditional 技术路径存在，但依赖明确条件或仍需补充有限证据。
    Unproven 尚无足够证据，不能据此形成可行性结论。
    Blocked 已知限制否定该主张，或必须修改 Outline / 采用替代路径。

    E0–E4 记录“凭什么知道”，不等同于上述判断状态。

    专项结论规则¶

    任一关键判断面 = Blocked
→ 专项通常为 Blocked；除非修改 Outline 主张或采用替代路径。

无 Blocked，但存在关键 Unproven
→ 专项为 Unproven；应优先补证据，不称为“有条件可行”。

关键路径均已验证，但存在外部条件
→ 专项为 Conditional；识别条件并路由至 [Under What Conditions](under-what-conditions.md)，再由 Integrated Assessment 指向 Readiness to Proceed / Risk & Control / Inception。

全部关键判断面均为 Supported
→ 专项为 Supported。

    使用 综合评估记录卡 记录每项判断面与专项结论，并关联具体 Outline claim、Stakeholder、Concern、Viewpoint / 最小 View、E0–E4 证据、条件和交接。

    6. 调查方向与交接¶

    Information Availability & Contextual Use¶

    调查：

    • 已展开的信息需求是否有候选源系统、知识源、规则源、事件源或记录来源？
    • 是否存在受支持的读取、查询、订阅、下载、引用、关联、过滤或回写路径？
    • 是否能与目标 Actor、Access Modality、业务对象、任务/案件、状态或时点建立正确关联？
    • 是否能使用 I&A 提供的角色、组织、团队、客户归属、案件责任、任务分派、租户或其他授权判断基础，执行信息访问范围？
    • 是否存在可复用的信息服务、知识服务、集成或事件能力？

    Information Trustworthiness & Fitness for Intended Use¶

    调查：

    • 对当前目标用途，能否明确或合理识别应依赖的权威来源？
    • 所取得内容是否保留来源、版本、生效状态、引用依据或必要历史上下文？
    • 时效、完整性、一致性与关联程度是否足以支撑预期使用？
    • 是否存在关键来源冲突、重复记录、不可解释内容或缺失，从而削弱该 Outline claim？

    跨线交接¶

    内容 主归属
    需要什么信息、知识、规则、业务对象、状态与证据，以及为何需要 Solution Outline
    需求分解、来源/访问/关联/范围执行路径，以及可信可用性的技术事实 Technology
    数据/知识 Owner、访问授权、来源维护、更新责任与前提是否可补齐 Readiness to Proceed
    数据分类、隐私、保密、审计、保留期、跨境与使用边界是否可接受 Risk & Control
    数据模型、知识库、数据管道、检索策略、RAG、详细接口与治理实现 Inception / Implementation

    一句话¶

    Information & Knowledge Enablement 先将 Outline 的初步信息需求拆为可核验的需求集，再判断这些内容是否可按正确业务上下文和访问范围取得，并以足够可信、可追溯、适用的形式支撑目标用途。
