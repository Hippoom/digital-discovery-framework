    Digital Discovery：场景适配与能力边界¶

    副标题：问题类型 × 能力组合 × 协调能力（含 Agent）定位

    用途：面对一个业务场景，判断它是否适合进入 Digital Discovery、应由哪些能力组合解决，以及在方向包含 AI/Agent 时，协调能力应承担什么角色、止步于哪里。

    本文是 Digital Discovery 的场景适配核心 Reference；它不预设解法必须是 AI 或 Agent。

    1. 本文回答什么，不回答什么¶

    回答¶

    面对一个业务场景，如何判断：

    1. 它是什么问题；
    2. 是否适合进入 Digital Discovery 并形成解决方案方向；
    3. 适合由哪些能力组合解决；
    4. 若方向包含 Agent，Agent 应承担什么角色、止步于哪里；
    5. 需要满足哪些前提，才值得进入下一步。

    不回答¶

    • 不决定是否投资、优先级和排期：由 Integrated Assessment 的价值与战略、投入与时机判断，以及 Decision Package / Gate 完成；
    • 不做详细工程设计：具体工程设计由相应建设路径承担；仅当方案方向包含 Agent 时，模型、RAG 形态、工具调用、权限实现、可靠性、评测和成本优化进入 Agent-enabled 专项工程实践。
    • 不替代风险与管控判断：合规、安全、隐私、审计、责任与残余风险由 Integrated Assessment 的 Risk & Control 评估线及相关评审形成结论。

    区分：适合 AI不等于值得投资。前者判断问题与能力是否匹配；后者还要在候选组合中比较价值、成本、风险和时机。

    2. 标准输出：场景适配结论¶

    本文不是介绍技术名词，而是为每个候选场景形成一份可复用的场景适配结论。

    输出 回答的问题 结论形态
    问题框定 它是什么问题？ 一个或多个问题类型、服务对象、目标动作
    解决方案适配结论 是否值得进入 Digital Discovery？是否需要 AI/Agent？ 适合 / 有条件适合 / 不适合（暂不适合）；标明 AI/Agent 是否适用
    能力组合建议 由哪些能力解决？ Rules / Workflow / ML / Optimization / GenAI 的主辅组合
    协调能力定位与边界 若采用 Agent：做什么、止步在哪？ 不需要 Agent / 助手 / 协调者+建议 / 受控执行
    前提与阻塞项 满足什么才进入下一步？ 需补齐的数据、规则、系统、责任、运营条件
    下一步建议 现在该做什么？ 进入方案设计 / 先补前提 / 转替代解决方案路径 / 停止或延后

    三档适配结论¶

    结论 含义 下一步
    适合 痛点、价值机制、能力匹配与运营条件基本清晰 进入方案设计与投资评估
    有条件适合 方向成立，但关键前提尚缺 先补数据、规则、流程、接口、Owner 或运营机制
    不适合 / 暂不适合 当前解决方案方向不成立，或问题、价值、行动闭环尚不成立 停止、延后，或转向规则/流程/数据治理/普通产品能力

    3. 五步判断法¶

    业务场景
  ↓
1. 问题识别：它是什么问题？
  ↓
2. 场景适配：它是否值得形成解决方案方向？AI/Agent 是否适用？
  ↓
3. 能力选型：由哪些能力组合解决？
  ↓
4. 协调能力定位：若采用 Agent，它做什么、止步在哪里？
  ↓
5. 前提检查：缺什么？是否可以进入下一步？
  ↓
场景适配结论

    原则：先识别问题，再定能力组合；只有能力与交互需要时才判断 AI/Agent，并进一步决定 Agent 角色。

    4. 第一步：问题识别——它是什么问题？¶

    先去掉“做个 XX Agent”之类的方案词，识别根问题类型。一个业务场景通常是多个问题类型的组合，不应强行只选一种。

    问题类型 核心问题 典型场景（示意）
    Classification 这是什么？ 商品打标、客户分群
    Knowledge / Evidence Inquiry 已有知识、事实或证据中，什么与当前问题相关？依据是什么？ 政策问答、产品知识问答、制度查询、专业流程咨询
    Execution 到哪一步了、下一步是什么？ 收货、调拨、工单处理
    Assessment 准备好了吗、是否满足条件？ 活动准备度、上线检查
    Prediction / Risk 未来会发生什么、风险多大？ 销售风险、断货风险
    Decision / Optimization 应该怎么做、如何在约束下求更优？ 选品、补货、排班、分货
    Generation 应该如何表达？ 客服回复、邮件生成、内容草稿

    “专业问答”不是天然单一的问题类型¶

    “回答专业问题”是面向用户的场景或交互形式，通常需要继续拆解。最常见的组合是：

    专业问答
= Knowledge / Evidence Inquiry（找到可信依据）
+ Generation（理解、解释与表达）

    它还可能叠加 Assessment、Execution 或 Decision。例如“我符合报销条件吗？” = Knowledge / Evidence Inquiry + Assessment。

    示例：智能补货不是一个单一问题¶

    智能补货
= Prediction（预测需求）
+ Decision / Optimization（在约束下计算补货策略）
+ Generation（解释建议）
+ Execution（发起或跟踪执行）

    5. 第二步：场景适配——是否值得进入 Digital Discovery？¶

    “技术上能做”不等于“值得形成解决方案方向”。本步判断是否存在成立的产品机会，并明确它是否需要 AI 或 Agent。

    判断 要问什么 不满足时的含义
    痛点成立 是否存在明确、高频、高损失或高价值的痛点？ 没有真实问题，不应做产品
    能力适配 是否涉及非结构化理解、预测、生成、优化或跨能力协调？ 可能应优先使用规则、流程、数据治理或普通系统
    行动闭环 结果是否进入真实工作流，并支持具体行动？ 容易成为“聪明但无用”的聊天界面
    人机价值 所选能力是否降低认知负担、扩大专家能力、提升决策质量或效率？ 价值不清，难以形成持续使用
    可运营性 是否有 Owner、反馈、数据/知识更新和效果度量机制？ 只能 Demo，难成为持续产品

    这里的重点不是打分本身，而是识别：价值机制是否成立，缺口在哪里，是否值得补。

    6. 第三步：能力选型——由哪些能力组合解决？¶

    能力边界¶

    能力 适合作为主能力 不应替代什么
    Knowledge Access / Information Retrieval 从文档、知识库、系统、数据库中获取相关、可信、已授权的事实与证据 不应默认用向量检索替代结构化查询或精确匹配
    Rules 条件清晰、规则稳定、需要确定性和可审计 不应用 LLM 替代明确规则
    Workflow 流程推进、状态流转、任务编排 不承担预测或最优决策
    ML 有历史样本，需要预测或分类 样本和口径不足时不能承诺预测能力
    Optimization 有明确目标函数、约束条件，需要更优解 不应让 GenAI“猜一个最优方案”
    GenAI 理解非结构化输入、解释、生成、交互 不应独自承担高风险确定性判断
    Agent 多步骤协调、跨能力调用、结果汇总和人机交互 不应只是给单点能力套聊天壳

    问题类型 × 主能力¶

    问题类型 Knowledge Access / Retrieval Rules Workflow ML Optimization GenAI
    Classification △ △ ❌ ✅ ❌ ✅
    Knowledge / Evidence Inquiry ✅ △ ❌ ❌ ❌ ✅
    Execution △ △ ✅ ❌ ❌ ✅
    Assessment △ ✅ △ ❌ ❌ ✅
    Prediction / Risk △ △ ❌ ✅ ❌ ✅
    Decision / Optimization △ △ ❌ △ ✅ ✅
    Generation △ ❌ ❌ ❌ ❌ ✅

    ✅ 主要能力；△ 辅助能力。能力组合创造价值；GenAI 常只是其中一环。

    RAG 的位置¶

    • RAG 不是问题类型，也不是基础能力类型；
    • RAG 是一种解决模式：Knowledge Access / Information Retrieval + GenAI + 基于证据的回答约束（如引用）；
    • 向量库、搜索引擎、Embedding、Rerank 等属于具体技术实现或检索策略；
    • Digital Discovery 决定需要何种信息与证据获取能力；当该方向采用 Agent 时，Agent-enabled 专项工程实践 决定具体采用何种检索实现及如何评测。

    7. 第四步：协调能力（含 Agent）定位——做什么，止步在哪里？¶

    仅当问题需要跨能力、多步骤协调或受控交互时，才进入本步。Agent 是协调者，不是天然的决策者：

    理解目标 → 拆解问题 → 调用能力 → 汇总结果 → 解释原因 → 与人交互。

    档位 Agent 角色 适合场景
    不需要 Agent 单一确定性能力或系统即可 规则判断、固定流程、单点查询
    解释 / 助手 解释结果、回答问题、生成草稿 低风险知识服务、辅助表达
    协调者 + 建议 调用能力并形成建议，由人确认 选品、补货、调价、经营分析
    受控执行者 在权限、幂等、可回滚、审批约束下执行 低风险、可逆、标准化动作

    Agent 的止步原则¶

    • 高风险判断交给规则、ML、优化器或人；
    • 高风险写操作默认人确认；
    • 需要最优解时使用Optimization；
    • 规则明确时使用Rules；
    • GenAI 主要承担理解、协调、解释和生成。

    详见：Agent 定位与边界。

    8. 第五步：前提检查——满足什么才值得进入下一步？¶

    此处检查的是进入方案设计、投资评估或工程实现前的前提条件，不替代对应建设路径的详细工程设计；Agent-enabled 方向的工程深化由 Agent-enabled 专项工程实践 承担。

    前提类别 要确认什么 不满足时的处理
    问题与指标 目标、成功标准、验收口径是否明确 先做痛点具象化和指标定义
    数据与知识 数据、知识、样本、业务口径是否可信可得 先做数据、语义或知识治理
    决策逻辑 规则、目标函数、约束、例外是否可表达 先沉淀规则、策略或专家知识
    系统与动作 是否有可接入系统、受控动作和反馈路径 先补接口、权限和流程
    责任与风险 Owner、确认者、责任边界、红线是否明确 先定义治理与人机边界
    运营条件 谁维护、如何评测、如何更新、如何复盘 先建立运营机制

    9. 输出到当前 Discovery 工件¶

    本 Reference 为 Solution Outline 的问题与能力主张提供输入；它不替代 Outline、Integrated Assessment 或 Gate。

    当前工件 / 评估线 本文提供的结论
    Solution Outline 问题类型与作用模式、主/辅能力组合、Agent 角色与自动化档位（如适用）、范围与红线、方向性接入/依赖、基本可运营性要求。
    Integrated Assessment — Solution Fit 场景适配结论、非 AI 替代路线、能力与行动边界是否自洽的输入。
    Integrated Assessment — Readiness to Proceed / Risk & Control 前提、阻塞项、Owner、确认者、责任边界和红线的输入；这些评估维度才判断前提是否可在下一承诺前补齐、控制是否充分、风险是否可接受。
    Decision Package / Gate 方向适配、条件与待验证项的汇总输入；Gate 才作 Go / Defer / No-go。
    Agent Harness（仅 Agent-enabled 方向） 获 Go 后的具体工程设计、验证与运营工程。

    与其他工件的边界¶

    场景适配结论
  → Solution Outline：问题、能力、角色、边界、方向性前提
  → Integrated Assessment：价值/适配、Readiness、Risk & Control、投入与时机的证据与判断
  → Decision Package / Gate：汇集条件与建议，作出正式决策
  → Agent Harness（仅 Agent-enabled 方向）：具体工程设计、验证与运营工程

    10. 三个快速示例¶

    场景 问题类型 适配结论 能力组合 Agent 档位 关键前提
    活动准备度 Assessment + Generation 适合 Rules 为主；GenAI 解释 解释 / 助手 准备度规则和责任人明确
    智能补货 Prediction + Decision/Optimization + Generation 有条件适合 ML + Optimization + Rules + GenAI 解释 协调者 + 建议 需求数据、约束、目标函数和人工确认机制
    首页选品 Decision / Optimization 有条件适合 Optimization 为主；GenAI 可解释 协调者 + 建议 业务目标、约束、实验和效果归因机制

    一句话¶

    先识别问题，再判断解决方案方向是否成立；先定能力组合；仅在需要跨能力协调时再定 Agent 角色；不满足前提，就先补前提。
