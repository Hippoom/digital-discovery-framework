    解决方案假设 — 形成 Playbook¶

    用途：配合 解决方案假设 — 形成 Workflow，帮助参与者将已澄清的 Business Opportunity（业务机会） 转化为一条或多条可比较、可被后续证据支持或削弱的 Solution Hypothesis（解决方案假设）。

    本 Playbook 提供推导路径、比较方法、质量标准与反例；活动位置、On Hold 与交接以 Workflow 为准；实际字段以 解决方案假设卡片 为准。

    1. 使用边界¶

    本 Playbook 假定业务机会已经澄清：已知其对象、情境、Problem / Need / Opportunity、当前做法或不作为、目标动作、价值机制、初步信号与关键边界。

    它帮助回答：

    • 可能以什么业务或服务方向回应这个机会？
    • 该方向为谁提供什么可观察的价值？
    • 它与当前做法或另一条方向有什么关键差异？
    • 当前先关注什么、不承担什么，以及什么会支持或削弱该判断？

    它不帮助回答：

    • 要组合哪些详细能力、是否采用 AI / Agent；
    • 应采用什么 Solution Archetype、服务触点、行动边界、架构或技术实现；
    • 数据、接口、权限、控制或组织前提是否已经具备；
    • 方案是否可行、ROI 是否成立、风险是否可接受或是否应进入 Gate。

    Solution Hypothesis 是“可能以什么方向回应”的可检验主张。正式的 L1 Solution Archetype 与能力展开属于后续 Solution Outline。

    2. 从业务机会推导方向假设¶

    不要从“做一个 App / 平台 / RAG / Agent”起草 Hypothesis。先保留 Opportunity 的业务语言，再把不同部分转化为方向主张：

    Business Opportunity 中已澄清的内容 转化为 Solution Hypothesis 的内容
    对象、情境、Problem / Need / Opportunity For / Who
    目标动作与价值机制 Provides
    当前做法、不作为或主要替代方式 Unlike
    初始范围、非目标、红线 初始范围 / Is NOT / 已知约束
    初步观察信号、事实、假设与待解问题 成功假设 / 事实、假设与待解问题

    2.1 形成一条最小方向主张¶

    可依次追问：

    1. For / Who：谁在什么机会或情境中需要被支持？
    2. Is a：可能以什么业务或服务方向回应？
    3. Provides：帮助其完成或改善什么目标动作，而不只是提供什么系统功能？
    4. Unlike / It：相对当前做法或替代方式，关键差异为何可能有价值？
    5. Is NOT：不替代哪些责任、不承诺哪些结果、不在当前范围内承担什么？
    6. 成功假设：什么业务结果或观察信号会支持或削弱这条方向？

    2.2 识别方向而非实现名称¶

    过早实现表达 可讨论的方向表达
    做一个交付风险 Agent 面向跨职能交付协同的风险理解与处置支持服务
    做一个知识库 帮助服务人员在咨询处理中获得可核验答复的知识支持服务
    上一个预测模型 面向计划人员的需求变化预警与处置支持方向
    做一个 App 面向现场角色的任务接收与异常协同服务方向

    右栏仍不是最终的 Solution Archetype 或能力架构；其作用只是让方向能够与 Business Opportunity 比较和验证。

    3. 形成与比较多个方向¶

    同一 Business Opportunity 可以有多个 Hypotheses。只在候选方向确有业务或服务差异时分开形成，例如：

    • 改善同一目标动作的服务方式不同；
    • 价值机制或主要受益对象不同；
    • 与当前做法相比的关键差异、责任边界或初始范围不同。

    不在此层比较：

    • 厂商、产品、模型、框架或技术栈；
    • 同一方向的不同实现方案；
    • 尚未形成业务或服务差异的“App / Agent / RAG”标签。

    比较时的最小问题¶

    比较维度 要问什么
    机会回应 哪条方向最直接回应 Opportunity 的对象、情境与目标动作？
    价值机制 它为何可能改善最终业务结果，而不只产生抽象使能成果？
    差异 它与当前做法或另一条方向的关键差异是否清楚？
    边界 它是否明确了不承担的责任、当前不覆盖的范围和已知红线？
    可验证性 是否能说明什么信号会支持或削弱该主张？

    每条候选方向分别使用一张 解决方案假设卡片，并通过 business_opportunity metadata 指向同一 Business Opportunity。不要在 BO Card 或某张 SH Card 正文维护备选清单。

    4. 设置范围、非目标与成功假设¶

    初始范围¶

    初始范围是当前最值得讨论或验证的对象、情境或业务范围，不是后续项目范围。它应避免方向因覆盖过广而失去可比较性。

    Is NOT 与已知约束¶

    Is NOT 应明确责任和承诺边界，例如不替代谁的决定、不自动执行什么、暂不覆盖哪些场景。已知约束仅记录已经影响方向选择的客户、监管、组织、时机或业务红线；不要把未核验的技术可行性结论写入此处。

    成功假设¶

    成功假设应连接 Opportunity 的目标动作、价值机制与初步观察信号：

    若 [对象] 能通过 [方向提供的支持] 更好地 [目标动作]，则预期改善 [最终业务结果]；可先观察 [信号]。若 [反向信号 / 关键前提不成立]，该方向被削弱。

    不要把“用户喜欢”“模型准确”或“完成 Demo”单独写成成功判断，除非能够说明其与目标动作和最终业务结果的连接。

    5. 常见误区¶

    误区 为什么不足 应如何调整
    将“做 Agent / RAG / App”直接写成 Is a 将实现或触点误作业务方向，无法与 BO 的价值机制比较 用业务或服务语言说明帮助谁完成什么目标动作
    一张 Card 写多个候选方向 方向差异、边界和成功假设无法分别讨论或验证 每条方向一张 Card；关系以 metadata 追溯
    只写“提供智能洞察” 没有说明实际改善什么动作或结果 写出对象、目标动作、价值机制和初步信号
    将能力架构或 Agent 角色写入 Hypothesis 抢占 Outline 的 L1 / 能力 / 交互展开 保留为后续待设计内容；只记录方向性价值主张
    把数据可用、风险可接受当作事实 将 Assessment 结论提前写入方向主张 标为事实、假设或待解问题，并在后续评估验证
    以“收益很大”替代成功假设 缺少支持或削弱判断的可观察路径 写出初步业务结果信号及会削弱主张的条件

    6. 使用后的最小检查¶

    在形成或更新 解决方案假设卡片 前，检查是否可以清楚回答：

    1. 是否能追溯到且仅指向一个 Business Opportunity？
    2. Is a 是否使用业务或服务语言，而非 Agent、RAG、平台或 App 等实现词？
    3. Provides 是否说明可观察的目标动作或价值，而非泛称“智能化”？
    4. Unlike / It 是否说明与当前做法或替代方式的实质差异？
    5. Is NOT 是否明确了真实的责任、承诺或范围边界？
    6. 成功假设是否能由业务结果或观察信号支持或削弱？
    7. 是否避免了 L1 Solution Archetype、能力组合、架构、数据/API 与实施内容？
    8. 若形成多条 Hypotheses，是否每条都单独记录而非混写？

    一句话¶

    从已澄清的业务机会出发，以业务或服务语言提出“可能如何帮助谁改善什么动作”的方向主张；每条方向独立记录、可比较且可被信号削弱，不抢占后续 Solution Outline 的 Archetype、能力和实现设计。
