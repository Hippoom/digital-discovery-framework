    解决方案纲要 — 形成 Playbook¶

    用途：帮助团队将一条 Solution Hypothesis 形成可评估的 Solution Outline，并保持 方案主张 与 综合评估结论 的边界。

    1. 使用方式与边界¶

    • 活动位置、输入输出、关系和退出条件见 解决方案纲要 — 形成 Workflow；
    • 字段和填写最小结构见 解决方案纲要卡片；
    • 能力类别、问题类型和 Agent 档位见 AI场景适配与能力边界；
    • Agent 的人与系统责任边界见 ../../Agent 定位与边界；
    • 技术证据、可行性和量级判断的方法见 技术参与 Digital Discovery：问题与方法。

    本 Playbook 回答如何形成“该方向需要是什么样”的方案主张；不判断数据是否具备、技术是否可行、风险是否可接受、ROI 是否成立或是否应通过 Gate。

    2. 三层对象，不混写¶

    对象 核心问题 应记录的内容 不应提前记录
    Business Opportunity 为什么值得探索？ 对象、情境、目标动作、价值机制、业务结果 服务或技术方向
    Solution Hypothesis 可能以什么方向回应？ 服务/价值方向、初始范围、非目标、成功假设 L1 Archetype、能力、服务触点、行动边界
    Solution Outline 该方向需要是什么样？ 场景、L1 Archetype、能力、服务触点、行动边界、方案需求与约束，以及方向性的 Ambition Roadmap 具备状态、证据结论、风险接受、成本/时机、Gate 建议
    Integrated Assessment 这些主张是否成立、具备且可接受，并且现在是否值得推进？ 价值与战略适配、解决方案适配、技术可行性、推进准备度、风险与管控、投入与时机的证据和判断 重复定义方案本身

    纲要中“需要受控动作与确认人”是需求；评估中“是否存在、可否获得、风险是否可接受”才是结论。

    3. 形成顺序¶

    3.1 从 Hypothesis 提取设计输入¶

    先提取并保持可追溯：

    Solution Hypothesis 已有内容 纲要中要展开的内容
    For / Who、初始范围 优先场景、目标对象、触发时点、目标动作
    Provides、It、成功假设 主要服务结果、问题/作用模式、价值机制的方案表达
    Is NOT、初始范围、已知约束 服务边界、行动边界、硬约束
    事实、假设与待解问题 设计假设、方案需求、需由 Assessment 验证的问题

    若无法说清 Hypothesis 的对象、价值、初始范围或非目标，应先返回 Stage 1 澄清，不以 L1 Archetype 替代方向判断。

    3.2 定义目标场景与目标动作¶

    优先选择能够体现价值机制、边界和行动闭环的场景。说明谁在什么触发点，需要理解、判断、协同、准备或完成什么动作，以及结果如何进入其真实工作。

    不要将“上线一个平台”“采用 Agent”当作目标动作；也不要将一个宽泛部门、所有用户或所有流程直接视为首个场景。

    Problem Types：作为 Scenario 分析透镜¶

    可借用 Service Blueprint 等方法形成 As-is Scenario Blueprint，再从其中提取 Observed Frictions & Failure Modes。这些是现象与信号，不自动等同于某种解决方案类型；应进一步判断其问题机制，并将下列 Problem Types 作为分析透镜：

    Problem Type 用于识别的主要问题机制
    Information & Sensemaking 信息缺失、分散、冲突、难以解释，或相关角色难以形成共同理解。
    Decision & Cognitive Workload 判断负担过高、规则难以应用、选项或影响难以比较。
    Coordination & Handoff 跨角色协作、责任交接、等待、重复沟通或升级失效。
    Workflow & Exception Handling 流程状态不清、任务遗漏、例外无法闭环，或既有路径无法适应实际情形。
    Work Execution & Automation 重复、规则明确或可受控的执行步骤仍需人工发起、搬运、更新、校验、触发或跟进；或者尚未定义可安全自动化的动作、触发、例外、确认、回退与责任边界。
    Record & Transaction Integrity 业务对象、状态、记录或交易的一致性、完整性或权威性不足。
    Control, Risk & Accountability 权限、审计、责任、合规或风险控制存在缺口，或限制可自动执行的范围。
    Experience & Access 角色无法在恰当触点及时获得、理解或使用所需支持。

    “工作不够自动化”应先归入 Work Execution & Automation，再按实际机制叠加其他类型：任务流转与升级问题通常同时涉及 Workflow & Exception Handling；信息搬运或核对也可能涉及 Information & Sensemaking 或 Record & Transaction Integrity；不能自动执行的原因可能落在 Control, Risk & Accountability。这组类型不构成 L1 Solution Archetype，也不预设 Agent；它们用于界定本轮的 Priority Design Interventions，随后形成 To-be Scenario Blueprint 与 Solution Outline。

    3.3 选择 L1 Solution Archetype 类型，并形成场景化表达¶

    L1 Solution Archetype 是可比较的方案主形态。每份 Outline 选择一个主类型，再以场景化表达说明其在当前 Opportunity / Hypothesis 下服务谁、处理什么业务对象或动作、产生什么结果。

    L1 标准类型 核心责任 不等于
    Insight & Monitoring（洞察与监测） 让事实、指标、状态、趋势与异常可见 仅有报表、Dashboard 或其他呈现触点
    Decision Support & Optimization（决策支持与优化） 预测、解释、情景比较、建议，以及约束下的人工决策支持 自动决策权或具体交互界面
    System of Record / Transaction Management（业务记录与交易管理） 维护权威业务对象、生命周期、状态与交易一致性 App、Portal 或单纯查询界面
    Workflow & Case Management（流程与案例管理） 管理任务、审批、路由；或围绕持续演变的事件、例外、案件进行协同、升级与闭环 单一固定步骤或仅面向用户的服务体验
    Knowledge & Expert Assistance（知识与专业辅助） 提供可核验知识、规则/政策解释与专业指导 自动业务执行或单纯的对话界面

    使用以下结构形成场景化表达：

    [该 L1 类型]，面向 [目标对象] 在 [优先场景 / 触发点]，
管理 / 支持 [业务对象或目标动作]，
以 [主要服务结果] 支持其工作。

    L1 类型用于区分方案类别，而不是贴技术标签。场景化表达也不承担其他维度：问题 / 价值作用模式用于辅助分析场景和能力组合；交互 / 服务触点说明如何获得结果；能力组合说明靠什么实现；非目标、责任限制和禁止动作记录在行动边界中。

    过早或过泛表达 类型 + 场景化表达
    做一个交付风险 Agent Workflow & Case Management：面向跨职能交付协同的风险理解、处置准备与人工确认服务，围绕持续演变的风险、待协调事项与责任流转提供处理闭环。
    做一个 RAG 知识库 Knowledge & Expert Assistance：面向服务人员的可核验知识解释与升级支持服务。
    上一个预测模型 Decision Support & Optimization：面向计划人员的需求变化预警、解释与处置准备服务。
    做一个 App 先判断其主类型；若管理权威订单对象，则可能是 System of Record / Transaction Management；若处理例外事项，则可能是 Workflow & Case Management。

    若两个类型分别构成实质不同的方案主张，应建立多份 Outline，而不是在同一 Card 中混写；若仅有一个支撑另一类型的局部能力，仍选择承担主要业务责任的主类型。

    3.4 形成 Ambition Roadmap¶

    Ambition Roadmap 是 Solution Outline 的方向性组成：在不承诺交付计划的前提下，说明若该方向成立，当前优先验证/建立什么，后续可能如何扩展价值、能力、范围或目标状态，以及什么条件会改变顺序。

    Current horizon
→ next ambition horizons
→ sequencing hypotheses / dependencies
→ conditions that may reorder, defer or stop the path

    它应满足：

    • 围绕价值/能力/范围增量，而不是工作包、精确日期或资源承诺；
    • 明确当前 horizon 与后续 ambition 的边界；
    • 记录可能改变顺序的依赖、证据、约束、风险或窗口；
    • 作为 Integrated Assessment 的 Readiness to Proceed、Risk & Control、Investment & Timing 输入；
    • 允许 Gate 只批准或 Defer 下一 investment horizon，而不自动批准整张 ambition。

    它不应：

    • 等同于 Inception 后的 delivery plan；
    • 以路线图名义选定技术架构、产品、平台、模型或实施路径；
    • 预先承诺预算、团队、日期、交付工作包或未经 Gate 批准的 future scope。

    3.5 组合能力、服务触点与行动边界¶

    依次说明：

    1. 能力组合：主/辅能力分别做什么；包括非 AI 路径，避免以 GenAI 或 Agent 覆盖 Rules、Workflow、Optimization 等明确责任。
    2. 服务触点：谁通过何种触点获得何类结果，结果如何进入下一步人或系统工作。
    3. 交互/编排/自动化：结果是被动呈现、按需查询、协同编排还是受控触发；只有跨能力、多步骤协调确有价值时才引入 Agent。
    4. 行动边界：哪些内容可解释、可建议、可准备、可受控执行；不替代哪些责任、不承担哪些决策；谁必须确认；哪些动作禁止；何时升级或人工接管。

    3.6 推导方案需求与待评估问题¶

    由能力和边界推导需要的知识、数据、规则、系统状态、受控动作、权限、可追溯性、责任、度量、更新和人工接管路径。用“需要 / 应具备 / 必须遵守”表述。

    将“数据质量是否足够”“接口是否可达”“规则是否能表达”“确认人是否可安排”“控制是否可验证”等写为待评估问题，而不是假定已经成立。

    4. 何时拆分 Outline，何时返回拆分 Hypothesis¶

    观察到的差异 应如何处理
    同一服务方向下，L1 Archetype、能力/交互形态或行动边界实质不同 为同一 SH 建立多张 Solution Outline Card，分别比较
    对象、价值机制、初始范围或服务方向已不同 返回 Solution Hypothesis，拆成不同方向
    只是同一纲要内的场景切片、措辞优化或未改变主张的细化 保持同一 Outline，更新其优先场景或字段
    只是模型、框架、接口、部署或实现路径不同 留给 Inception，不应以此拆分 Outline

    不在 SH Card 或 Outline Card 正文维护反向清单；上游关系只由 Outline 的 solution_hypothesis metadata 记录。

    5. 常见误区¶

    误区 修正方式
    把 L1 Archetype 写成“Agent / RAG / App / 平台” 回到对象、场景、服务结果和行动档位，用实现中立语言表达
    把“数据已具备”“已合规”“风险可接受”写进纲要 改为方案需求或待评估问题，交给 Integrated Assessment 形成结论
    用一张 Card 混合多个实质不同的方案形态 按 L1、能力/交互或行动边界拆成多张 Outline Card
    用能力清单替代服务设计 明确服务触点、结果和结果如何进入真实工作
    默认 Agent 负责决策或执行 先说明 Rules / Workflow / ML / Optimization / GenAI 的责任；只在协调价值成立时定义 Agent，并明确确认与禁止动作
    把纲要深化为架构设计 停在方向性能力、需求与边界；模型、接口、权限、控制实现和详细运营设计进入 Inception 及后续实践

    6. 质量检查¶

    形成或评审 Outline 前，检查：

    • 可沿 solution_hypothesis 追溯至唯一 SH，并间接追溯至 BO；
    • 优先场景、目标对象、目标动作和主要服务结果清楚；
    • L1 Solution Archetype 说明方案形态，而不是技术或产品名称；
    • 能力分工、服务触点和行动边界相互一致，且不默认 Agent；
    • 所有数据、规则、权限、责任和可运营性表述为需求、约束或待验证问题，而非已具备结论；
    • 不包含模型、架构、接口、部署、精确估算、风险接受或 Gate 建议；
    • 纲要足以成为 Integrated Assessment 的评估对象。

    一句话¶

    解决方案纲要先把方向假设收敛为“在何种场景、以何种方案形态、由哪些能力、通过哪些服务触点、在何种行动边界内创造价值”的主张；再由综合评估判断它是否具备证据、条件与可接受性。
