    业务机会 — 框定 Playbook¶

    用途：配合 业务机会 — 框定 Workflow，帮助参与者把原始诉求、变化信号或痛点，澄清为可探索的 Business Opportunity（业务机会）。

    本 Playbook 提供分析路径、提问方式、质量标准与示例；活动位置、输入输出、On Hold 与后续交接，以 Workflow 为准；实际 Opportunity 的记录字段以 业务机会卡片 为准。

    1. 使用边界¶

    适用于 Stage 1 中出现以下任一输入时：

    • 某个角色或团队正在承受问题、摩擦、损失或风险；
    • 存在尚未被满足的业务、客户、员工、合作伙伴或监管需求；
    • 出现市场、政策、组织、技术或能力窗口带来的新机会；
    • 提出者以“做报表 / 做 App / 换 OMS / 做 AI / 做 Agent”等方案语言提出诉求。

    本 Playbook 用于回答“为什么值得探索”，而不是：

    • 选择实现方案、能力组合或技术产品；
    • 证明价值已成立、完成 ROI、确认投资优先级；
    • 证明数据、技术、风险或运营前提已经具备；
    • 将业务机会直接写成一个 Solution Hypothesis。

    2. 将原始诉求还原为 Problem / Need / Opportunity¶

    先保留提出者的原话及其意图，但不将其预设方案当作结论。识别该诉求主要由哪种触发类型引起；一项 BO 可以同时包含多种类型。

    触发类型 要澄清什么 常见信号
    Problem（问题） 当前什么没有按预期发生，造成什么摩擦、损失、风险或体验问题 延误、返工、错误、投诉、重复协调、风险事件
    Need（需求） 哪个对象在什么情境下需要完成什么，却缺少必要服务、信息、能力或支持 无法获得信息、无法完成服务、覆盖不足、响应不足
    Opportunity（机会） 什么变化或窗口使得创造新价值、改善现有服务或扩大覆盖成为可能 新市场、政策变化、新渠道、组织调整、能力窗口

    从方案线索追问业务机会¶

    “需要一个报表 / App / 新 OMS / Agent”
  ↓
谁在什么情境下需要改善什么？
当前做法或不作为为什么不足？
他们需要作出什么判断、完成什么行动或获得什么服务？
若不改变，损失、风险或错失机会是什么？

    Note

    “问题、需求、机会”是 BO 的触发和当前缺口，不是未来方案名称。报表、App、OMS、AI、Agent 等只保留为初始方案线索，供后续形成或比较 Solution Hypotheses 时检验。

    3. 澄清对象、情境、当前做法与目标动作¶

    用可观察的事实描述 BO，避免只有“效率低”“体验不好”“需要智能化”这类抽象判断。

    要素 应回答的问题 可接受的表达特征
    对象 谁受到影响、承担工作或承受后果？ 角色、客户群、合作伙伴、业务单元或受影响对象清楚
    情境 在什么触发事件、流程节点、时间窗口或工作条件下发生？ 能说明发生时机、范围或触发条件
    当前做法 / 不作为 现在如何处理；为何无法充分满足需要或抓住机会？ 能说明现状、摩擦、缺口、损失或限制
    目标动作 受影响对象需要更好地完成什么判断、行动、协作或服务？ 可被观察、讨论和后续验证，不是泛化感受

    质量检查¶

    若无法回答以下任一问题，优先继续澄清，而不是转向方案讨论：

    • 受影响对象是谁？
    • 何时、何地或在什么条件下问题 / 需求 / 机会出现？
    • 当前做法或不作为为什么不足？
    • 希望让对象更好地完成的具体动作是什么？

    4. 从目标动作到最终业务结果¶

    价值不应只是“营收 / 成本 / 风险”的标签。优先建立以下价值链：

    改善什么目标动作或工作条件
  → 通过什么机制产生改变
  → （如适用）形成什么使能成果 / 中间结果
  → 最终预期影响什么业务结果
  → 以什么初步信号支持或削弱判断

    例如：

    更早识别订单异常并明确责任人
  → 缩短异常发现到处置启动的时间
  → 形成跨角色共享的风险理解与处置重点
  → 降低履约延误和客户体验损失
  → 观察异常处置启动时间、延误订单比例和重复追踪量

    Note

    Stage 1 只需形成方向性价值主张和可观察信号；不要求准确归因、完整指标树、正式基线或 ROI 模型。

    最终业务结果¶

    最终业务结果描述该 Opportunity 最终希望影响的业务后果。一个 BO 可涉及多类结果；选择最能描述预期改变的类别即可。

    类别 典型结果 常见观察信号（示意）
    增长与商业结果 转化、留存、收入、客单、市场覆盖或商业机会实现 转化率、复购、收入、流失、线索到成交周期
    成本、效率与产能 减少手工工作、等待、返工、处理成本或释放能力 处理时长、吞吐量、人工介入量、返工率、单位成本
    服务、体验与响应 提升响应速度、可获得性、一致性或客户/员工体验 首次响应、一次解决率、满意度、转人工率、服务可用性
    质量、准确性与一致性 减少错误、提升标准执行或结果稳定性 错误率、命中率、差异率、复核通过率、质量投诉
    风险、合规与韧性 降低违规、损失、失控、欺诈、断供或运营中断风险 风险事件、违规率、审计发现、恢复时间、控制覆盖率

    使能成果 / 中间结果¶

    以下成果通常有价值，但多数情况下不是 BO 可以单独成立的最终价值结论。应将其写为通向最终业务结果的机制、中间结果或待验证假设。

    类别 典型成果 需要继续说明什么
    信息可得性与共同事实 信息更及时、完整、可解释；跨角色形成共同口径 它将改善谁的什么动作，并最终影响哪项业务结果
    决策与协同质量 更及时、更一致地判断；更好地在约束下配置资源；减少协调反复 判断或协同改善如何转化为服务、成本、质量、增长或风险结果
    组织能力与知识复用 专业经验可复用、降低关键人依赖、缩短上手时间、扩大覆盖范围 能力提升将如何改变工作条件或产出，并最终影响哪项业务结果
    控制与可追溯能力 责任更清晰、过程可追溯、例外更可见、控制执行更稳定 控制改善将如何降低具体风险、合规暴露、损失或质量问题

    必须保持以下链路：

    使能成果 / 中间结果
  → 改善什么目标动作或工作条件
  → 最终影响哪项业务结果
  → 用什么初步信号支持或削弱该判断

    Warning

    不将“提高决策质量”“形成知识库”或“增强可追溯性”单独写成 BO 的最终价值结论；若尚不能说明其如何通向最终业务结果，应保留为待验证假设或待解问题。

    5. 形成可讨论的 Opportunity 表达¶

    业务机会卡片 的两个核心字段应分工，而不是重复描述同一件事：

    字段 要回答什么
    问题 / 需求 / 机会陈述 现在发生什么或缺少什么；谁在什么情境下受影响；当前做法或不作为为什么不足。
    期望业务结果 通过什么预期改善机制，使对象能够更好地完成什么目标动作；最终希望改善什么业务结果，以及以什么信号初步观察。

    推荐写法¶

    问题 / 需求 / 机会陈述：

    在 [情境] 中，[对象] 正面临 [问题 / 未满足需求 / 新机会]；当前通过 [当前做法 / 不作为] 处理仍不足，因为 [摩擦、损失、风险或错失机会]。

    期望业务结果：

    通过 [预期改善机制]，使 [对象] 能够更好地 [目标动作]，预期改善 [最终业务结果]；初步可观察 [信号]。

    若需表达使能成果 / 中间结果：

    先形成 [使能成果 / 中间结果]，从而 [改善目标动作或工作条件]，预期改善 [最终业务结果]；初步可观察 [信号]。

    示例：避免只写抽象收益¶

    不够具体 更可讨论的写法
    提升效率 通过缩短薪酬咨询从受理到获得可核验答复的时间，使员工和 HR 能够更快完成咨询处理，预期减少处理成本并提升服务响应；初步观察处理周期、一次解决率和转人工比例。
    降低风险 通过更早识别可能影响客户交付的变化并启动协同处置，使相关角色能够更及时地处理异常，预期降低履约延误和客户体验损失；初步观察风险发现提前量、处置启动时间和延误订单比例。
    增加收入 通过帮助一线在客户咨询时更快给出有依据的产品建议，使其能够更好地完成推荐，预期改善转化与留存；初步观察推荐采纳、后续转化和投诉/退换信号。
    提高决策质量 先形成在既定服务水平和库存约束下可比较的策略建议，使计划人员能够更快作出资源配置判断，预期改善服务水平并减少库存占用；初步观察策略计算周期、例外覆盖、服务水平和库存占用变化。

    6. 区分事实、假设与待解问题¶

    不要为了形成 BO 而将不确定内容写成事实。

    类型 含义 处理方式
    事实 已有来源、记录或 Owner 支持的现状 注明来源或待核验状态
    假设 暂按成立、但可能影响探索方向的判断 标为待验证，不写成结论
    待解问题 当前未知且会影响是否或如何形成方向的问题 指定下一步澄清，或保留为未决项
    初始方案线索 提出者预设的报表、App、OMS、AI/Agent 等表达 保留来源，但不作为 BO 或 Hypothesis 结论

    7. 常见误区¶

    误区 为什么不足 应如何调整
    将“做一个报表 / App / Agent”写成机会 预设方案掩盖了真实问题、需求或机会 保留为初始方案线索，追问对象、情境、目标动作和当前缺口
    只写“效率低、体验不好” 没有对象、情境、动作或后果，无法判断是否值得探索 写清谁在何情境下无法完成什么，以及当前做法为何不足
    只写“提高决策质量、知识复用、可追溯” 多数是使能成果，不能独立说明最终价值 明确其如何改善目标动作，并连接服务、成本、质量、增长或风险结果
    直接承诺“降本 X%、提高收入 Y%” Stage 1 通常尚无完整基线、归因或 ROI 证据 写成待验证的价值方向和初步观察信号
    用 Demo 代替机会澄清 Demo 可能证明技术可展示，却不证明业务机会或价值机制成立 先澄清 BO；技术验证留给后续 Outline / Assessment

    8. 使用后的最小检查¶

    在形成或更新 业务机会卡片 前，检查是否可以清楚回答：

    1. 这是 Problem、Need、Opportunity，还是它们的组合？
    2. 谁在何种情境下受到影响？
    3. 当前做法或不作为为何不足？
    4. 需要改善的目标动作是什么？
    5. 价值机制如何通向至少一项最终业务结果？
    6. 若使用使能成果 / 中间结果，是否已写明其最终业务结果连接？
    7. 哪些内容是事实、假设、待解问题或初始方案线索？
    8. 是否存在至少一个初步观察信号，用于支持或削弱价值判断？

    一句话¶

    先将原始诉求澄清为 Problem / Need / Opportunity，再说明对象、情境、目标动作与价值机制；使能成果必须通向最终业务结果，方案词只能作为后续待检验的线索。
