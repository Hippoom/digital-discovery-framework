    解决方案纲要卡片¶

    1. 用途¶

    用于记录并追溯 Stage 2 中针对一条 Solution Hypothesis 形成的可评估方案主张。Card 记录 Solution Outline，不执行从 Hypothesis 到 Outline 的流程转换。

    活动位置、输入输出、关系与交接见 解决方案纲要 — 形成 Workflow；形成方法、拆分规则和质量检查见 解决方案纲要 — 形成 Playbook；本 Card 只保留填写所需的最小提示。

    • 回答：优先服务什么场景和动作；方案采用什么 L1 Solution Archetype；需要什么能力、服务触点、行动边界、信息/行动条件、设计假设与硬约束。
    • 不回答：这些条件是否已具备、证据是否充分、技术是否可行、风险是否可接受、成本/周期量级、是否应投入或通过 Gate。

    纲要是方案主张（proposition）：使用“需要 / 应具备 / 必须遵守”的表达。Integrated Assessment 才记录“是否具备、是否可信、是否可接受”的证据与判断。

    L1 Solution Archetype 是本 Card 的必填字段：用实现中立语言概括方案的服务、交互或自动化主形态；它不是独立 Card、流程节点，也不是“App / Agent / RAG / 平台”等技术或产品标签。

    2. 模板¶

    关系（必填）¶

    要填写什么 内容
    solution_hypothesis [在本 Card 的 metadata 中，链接到唯一来源的解决方案假设卡片。通过该 Hypothesis 的 business_opportunity metadata 回溯到业务机会；不在此重复维护 BO 关系。]

    方案主张（必填）¶

    要填写什么 内容
    一句话方案主张 [在何种优先场景，为谁，以何种实现中立的方案形态，支持什么目标动作或结果，并止于何种行动档位。]
    优先场景与触发点 [当前优先解释清楚的场景、业务变化或触发时点；不等于完整交付范围。]
    目标对象与目标动作 [谁需要完成、改善、理解、判断、协同、准备或受控执行什么动作。]
    主要服务结果 [用户或下游工作获得什么结果，以及结果如何进入真实工作。]
    问题 / 价值作用模式 [当前场景需要解释、预测、判断、协同、优化或其他何种作用模式；按需参考 AI场景适配与能力边界。它是形成能力组合的辅助分析，不定义 L1。]

    L1 Solution Archetype（必填）¶

    要填写什么 内容
    L1 Solution Archetype 类型 [从下列受控词表选择一个主类型：Insight & Monitoring（洞察与监测）；Decision Support & Optimization（决策支持与优化）；System of Record / Transaction Management（业务记录与交易管理）；Workflow & Case Management（流程与案例管理）；Knowledge & Expert Assistance（知识与专业辅助）。]
    L1 场景化表达 [结合本场景说明该类型服务谁、管理/支持什么业务对象或动作、产出什么结果；使用实现中立语言。交互触点、能力组合与行动边界在后续字段说明。]

    L1 类型是可比较的方案类别；场景化表达是其在当前 Opportunity / Hypothesis 下的具体主张。每份 Outline 选择一个主类型；若不同类型分别构成实质不同的方案主张，应分为多份 Outline Card。

    能力、服务触点与交互方向（必填）¶

    要填写什么 内容
    主能力与职责 [主能力分别做什么；使用业务/能力语言，不写模型、框架或具体实现。]
    辅助能力与职责 [支撑主能力的 Rules、Workflow、Knowledge Access、ML、Optimization、GenAI 等能力及其职责。]
    服务触点与结果进入方式 [谁在何处、以何种方式获得结果；结果如何进入后续人或系统工作。]
    交互 / 编排 / 自动化方向 [按需说明按需交互、协同编排、流程触发或自动化方向；若采用 Agent，说明其协调价值与角色，不默认采用。]

    行动边界与方案需求（必填）¶

    要填写什么 内容
    行动边界（含非目标） [哪些内容可解释、可建议、可准备、可受控执行；不替代哪些责任、不承担哪些决策，以及哪些动作不做或禁止。]
    确认、升级与人工接管方向 [谁确认什么；什么情形升级、转人工、停止或回退。]
    信息与规则需求 [需要哪些知识、数据、规则、约束、证据来源、系统状态与可追溯性。]
    行动、系统与权限需求 [需要哪些受控动作、系统状态、接口能力或权限边界；不写其已具备结论。]
    基本可运营性要求 [方案需要何类 Owner、基本度量、更新与人工接管路径；不设计完整 SLA、告警、评测或运行机制。]

    Ambition Roadmap（必填，方向性）¶

    Ambition Roadmap 是本 Solution Outline 的方向性规划组成，不是独立生命周期对象、Gate 决策、交付计划或成本承诺。它描述“如果方向成立，希望沿什么 horizon 扩展价值、能力或范围”；Integrated Assessment 判断近期 horizon 的排序、依赖、准备度、风险、投入和时机是否可信，Gate 只批准或 Defer 下一 investment horizon。

    要填写什么 内容
    当前 horizon [当前希望先验证、建立或推进的价值/能力/范围增量；不写交付工作包、精确日期或承诺资源。]
    后续 ambition horizons [后续可能扩展的价值、能力、范围或目标状态；按方向性顺序表达。]
    排序假设与依赖 [什么价值假设、前提、外部依赖、条件或证据会影响 horizon 的顺序、范围或是否继续。]
    不承诺什么 [明确不承诺的详细交付计划、成本、日期、技术方案或未经 Gate 批准的 future scope。]

    设计假设、约束与 Assessment 交接（必填）¶

    要填写什么 内容
    设计假设 [当前方案依赖哪些业务、技术、运营或管控判断；使用假设语气。]
    硬约束 / 红线 [必须遵守的业务、责任、监管、安全、隐私或其他边界。]
    关键待评估问题 [需要由 Integrated Assessment 判断的价值与战略适配、解决方案适配、技术可行性、推进准备度、风险与管控、投入与时机问题。可记录待评估的 Stakeholder Concern（如“关键链路在依赖不可用时需要受控降级”）；按 DFX 最小映射 选择 Viewpoint / Perspective 由 Assessment 完成，不在此写可行性、风险接受或详细运行设计结论。]

    1 Solution Hypothesis → 0..n Solution Outlines。若 L1 Archetype、能力/交互形态或行动边界存在实质差异，分别使用多张 Card；若对象、价值机制、初始范围或服务方向改变，应返回 Solution Hypothesis 层拆分。Card 不维护反向清单。

    3. 示例¶

    示例只说明 Solution Outline 的填写粒度，不代表条件已具备、技术已验证、风险已接受或获得投资批准。

    示例：交付风险协同支持纲要¶

    solution_hypothesis: "`交付风险协同支持`"

    方案主张（必填）¶

    要填写什么 示例内容
    一句话方案主张 在制造单元出现影响交付的变化时，为计划、生产、采购与质量相关人员提供共同的风险理解、处置准备与人工确认支持。
    优先场景与触发点 生产、供应、设备或质量状态变化可能影响近期客户交付时。
    目标对象与目标动作 跨职能相关人员需要共同理解影响、明确待协调事项，并准备由责任人确认的处置动作。
    主要服务结果 形成有依据的风险视角、影响说明、待协调事项和待确认处置建议，进入既有协同与责任流程。
    问题 / 价值作用模式 Prediction / Risk + Assessment + Execution 支持；跨职能协同。

    L1 Solution Archetype（必填）¶

    要填写什么 示例内容
    L1 Solution Archetype 类型 Workflow & Case Management（流程与案例管理）
    L1 场景化表达 面向跨职能交付协同的风险理解、处置准备与人工确认服务；围绕持续演变的交付风险、待协调事项与责任流转提供处理闭环。

    能力、服务触点与交互方向（必填）¶

    要填写什么 示例内容
    主能力与职责 风险识别与影响关联能力形成共同风险视角；Rules / Workflow 支持明确规则、状态和责任流转。
    辅助能力与职责 Knowledge Access 提供可核验的相关事实；GenAI 可解释跨来源信息；Optimization 仅在后续明确目标与约束时考虑。
    服务触点与结果进入方式 在既有交付协同触点向相关角色呈现风险、依据、待协调事项与待确认建议，并回到既有责任流程。
    交互 / 编排 / 自动化方向 以解释与协同准备为主；若需要跨能力汇总，可采用协调者 + 建议角色，但不自动作出正式处置。

    行动边界与方案需求（必填）¶

    要填写什么 示例内容
    行动边界（含非目标） 可以解释变化与潜在影响、提出待协调事项和准备建议；不替代生产排程、采购决策、质量放行或客户承诺的责任人；不得调整排程、下达采购、放行质量或向客户作出承诺。
    确认、升级与人工接管方向 对处置建议由相应责任人确认；影响无法解释、证据冲突或涉及红线时升级至人工协同。
    信息与规则需求 需要可追溯的生产、供应、设备、质量和交付相关状态、规则与责任边界。
    行动、系统与权限需求 需要读取相关状态并向既有协同流程提交受控待办或建议的能力；权限边界须由后续评估确认。
    基本可运营性要求 需要明确业务、规则/知识与技术问题的 Owner，定义基本风险、任务质量和人工接管信号。

    设计假设、约束与 Assessment 交接（必填）¶

    要填写什么 示例内容
    设计假设 相关变化能够形成对交付影响有意义的共同口径；责任人能在既有协同流程中确认处置。
    硬约束 / 红线 正式生产、采购、质量和客户承诺仍由对应责任人作出；需要保留依据与责任追溯。
    关键待评估问题 相关状态是否可信且可获得；风险关联是否具备足够准确性；权限、管控和人工确认路径是否可接受；投入与时机是否支持推进。
