    解决方案纲要 — 形成 Workflow¶

    At a glance¶

    Use when
    A Solution Hypothesis is ready to become a stable, assessable Solution Outline.

    Produce
    A Solution Outline proposition with L1 Archetype, Ambition Roadmap, requirements, assumptions and constraints.

    Next
    Use Integrated Assessment to gather evidence and judgement against the stable Outline.

    Canonical detail

    解决方案纲要 — 形成 Workflow¶

    用途：定义 Digital Discovery Stage 2 中，如何将一条可推进的 Solution Hypothesis（解决方案假设） 展开为可评估、可供 Gate 使用的 Solution Outline（解决方案纲要）。

    本文件定义活动位置、输入输出、关系、状态与交接；形成方法见 解决方案纲要 — 形成 Playbook；实际记录字段见 解决方案纲要卡片。

    1. 在工作流中的位置¶

    Business Opportunity
  ↓
Solution Hypothesis
  ↓
解决方案纲要 — 形成
  ├─ 1 个或多个 Solution Outlines
  │            ↓
  │     Integrated Assessment
  │            ↓
  │     Decision Gate
  └─ 需要重定方向：返回 Solution Hypothesis 形成 / 比较

    本活动属于 Digital Discovery 工作流 Stage 2“形成解决方案纲要与综合评估”。它接续 解决方案假设 — 形成 Workflow，并为综合评估提供方案主张；Card 仅记录一条纲要，不执行流程转换，也不替代本活动。

    2. 目的与边界¶

    目的¶

    把“可能以什么方向回应”的 Solution Hypothesis，展开为“该方向需要是什么样”的方向性方案主张。每条 Solution Outline 至少说明：

    • 优先服务哪些场景、对象和目标动作；
    • L1 Solution Archetype：选择何种标准方案类别，并以场景化表达说明其主要业务责任与服务结果；
    • 主/辅能力分别承担什么，用户或下游工作如何获得结果；
    • 解释、建议、受控执行分别止于哪里，谁确认、哪些动作禁止；
    • 为该方向需要哪些信息、规则、系统状态、受控动作、权限、责任与基本可运营性条件；
    • 当前设计假设、不可违反的约束，以及需要交给评估验证的问题。

    不在此活动中完成¶

    • 宣称数据、知识、接口、权限、责任或运营条件已经具备；
    • 形成技术可行性、证据等级、风险接受性、成本/周期量级或投资时机结论；
    • 选择模型、框架、RAG 策略、工具、接口、部署或详细架构；
    • 设计审批实现、权限与审计实现、完整验证方案、SLA、告警或运行手册；
    • 作出 Go / Defer / No-go 建议。

    硬边界：Solution Outline 是方案主张（proposition），说明“需要什么、边界在哪里”；Integrated Assessment 是证据与判断（evidence and judgement），说明“是否具备、是否可信、是否可接受、是否现在推进”。

    3. 输入与参与¶

    最小输入¶

    • 一条可推进的 Solution Hypothesis，及其来源 Business Opportunity；
    • Hypothesis 中的初始范围、非目标、价值主张、成功假设、已知约束与待解问题；
    • 已知的业务、技术、数据、管控或运营事实，只作为设计输入或待验证线索，不抢先写成评估结论。

    参与与责任¶

    • Solution Lead 组织纲要形成，保持与 Solution Hypothesis 的可追溯关系，并协调业务、技术与关键职能输入；
    • SA Lead / 等效方案设计责任 主导场景探索与 To-be 设计：组织 As-is / To-be Scenario Blueprint、识别问题机制、形成并排序 Design Interventions，并将其收敛为方案主张；该角色尚未正式配置时，由 Solution Lead 安排等效责任并记录待补足的 SA 方法与责任；
    • 业务/领域相关方 澄清优先场景、目标动作、业务规则、责任和不可违反的边界，并验证 As-is / To-be 的业务真实性；
    • Technology Lead 提出能力组合、非 AI 替代路径、方向性需求与技术约束；识别信息、系统、自动化、控制与可运营性依赖，但将可行性和量级结论留给综合评估；
    • 关键相关职能方 提出管控、数据、运营、财务或其他专业约束和待验证问题。

    角色责任以 Digital Discovery 治理与责任模型 为准；本 Workflow 对 SA Lead / 等效方案设计责任的表述用于定义应承担的工作，不替代后续 Operating Model 的正式 RACI 收敛。

    未来边界：Solution Operating Model 的方法、模板、必填字段、评估标准和 SA Lead 的正式工作产物，留待后续 SA Lead-owned workstream 定义。当前的 Digital Discovery 治理与责任模型 是本 Framework 的治理/RACI 定义，不是任何具体 Solution 的 Operating Model。

    4. 活动逻辑¶

    4.1 从方向主张收敛优先场景与目标动作¶

    从 Hypothesis 的价值、初始范围和非目标中选择当前需要解释清楚的优先场景、目标对象、触发时点和目标动作。该切片用于定义方案主张，不等于后续实施计划或交付范围。

    4.2 形成 Scenario Exploration Chain¶

    Solution Outline 的探索以场景及其工作机制为对象；可借用 Service Blueprint，但不将分析限缩为客户服务或体验设计。框架规定以下最小链路：

    As-is Scenario Blueprint
  → Observed Frictions & Failure Modes
  → Problem Mechanisms / Problem Types
  → Priority Design Interventions
  → To-be Scenario Blueprint
  → Solution Outline
    环节 目的 最小输出 主要责任
    As-is Scenario Blueprint 说明当前场景中角色、目标任务、触点、信息、决策、系统、规则、责任交接、控制与例外如何实际发生。 可复述的当前场景摘要；关键角色、任务、交接和证据/信息流。 SA Lead / 等效方案设计责任主导；业务/领域相关方验证。
    Observed Frictions & Failure Modes 区分已观察到的摩擦、失效、等待、返工、信息断裂、例外或控制问题，不将现象直接当作方案。 与具体场景、角色和任务关联的观察项。 SA Lead / 等效方案设计责任组织；业务、运营、技术及其他职能提供事实。
    Problem Mechanisms / Problem Types 判断摩擦或失效为何发生、属于何类问题，避免把“自动化不足”“需要 AI”等表象直接变成解决方案。 已识别的问题机制及适用的 Problem Types；需要继续验证的归因假设。 SA Lead / 等效方案设计责任整合；Technology Lead 提供技术与自动化机制输入。
    Priority Design Interventions 选择本轮准备改变的工作、信息、协同、决策、记录、控制或行动机制。 已排序、边界清楚的设计介入项；不以功能、产品或技术名称替代。 SA Lead / 等效方案设计责任主导；Solution Lead 确保与 Hypothesis 的价值主张一致。
    To-be Scenario Blueprint 表达设计介入后角色、任务、信息、责任、决策、控制及行动闭环应如何变化。 目标场景摘要；主要机制变化、预期服务/工作结果和未决假设。 SA Lead / 等效方案设计责任主导；业务验证；Technology Lead 塑形技术依赖与约束。

    此链路定义框架要求的活动、接口与最小产出；具体 Blueprint 模板、分析方法组合、优先级规则、主持方式和质量标准由 SA Lead 后续细化。Scenario Exploration Chain 是形成 Solution Outline 的最小活动/接口链，不是 Solution Operating Model 的静态方法或模板。Problem Types 是跨业务与技术的分析透镜，不是 L1 Solution Archetype，也不预设特定技术或 Agent。

    4.3 定义 L1 Solution Archetype¶

    基于相对明确的 To-be Scenario Blueprint，先从标准类型中选择方案承担主要业务责任的主形态：Insight & Monitoring、Decision Support & Optimization、System of Record / Transaction Management、Workflow & Case Management 或 Knowledge & Expert Assistance。再用实现中立语言说明该类型在当前场景服务谁、管理或支持什么业务对象/目标动作，以及提供什么主要结果。

    L1 Solution Archetype 是 Solution Outline 的必填结构字段，不是独立 Card、流程节点或 Agent 标签。它不以“做一个 App / Agent / RAG / 平台”代替类型选择与场景化主张；问题 / 价值作用模式在场景与能力分析中说明，交互/服务触点、能力组合和行动边界分别在对应字段说明，非目标和责任限制在行动边界中说明。

    4.4 形成 Ambition Roadmap¶

    在不承诺详细交付的前提下，记录该 Solution Outline 若成立时的当前 horizon、后续 ambition horizons、价值/能力/范围增量、排序假设、依赖和可能改变顺序的条件。Ambition Roadmap 是 Solution Outline 的方向性规划组成，不是独立生命周期对象或 Gate 决策。

    它为 Integrated Assessment 提供近期 horizon 的 Readiness to Proceed、Risk & Control、Investment & Timing 输入；Decision Gate 只批准或 Defer 下一 investment horizon，不自动批准整张 ambition。Inception 才将获 Go 的 horizon 深化为详细交付安排。

    4.5 形成能力、服务触点与行动边界¶

    说明主/辅能力的责任分工、结果如何进入用户或下游工作、必要时的交互/编排/自动化方式，以及解释、建议、执行、确认、升级、人工接管和禁止动作的方向性边界。只有协调价值明确时才定义 Agent 角色与自动化档位。

    4.6 从方案主张推导需求、假设与约束¶

    将所需知识、数据、规则、约束、系统状态、受控动作、权限、可追溯性以及基本可运营性条件写成“需要 / 应具备”的方案需求；记录设计假设、硬约束和待验证问题。不要把“是否已具备”写入纲要。

    5. 最小输出与记录¶

    本活动的最小输出是一条或多条由 解决方案纲要卡片 记录的 Solution Outline。每条纲要至少包括：

    1. 对唯一来源 Solution Hypothesis 的 solution_hypothesis metadata 关系；
    2. As-is / To-be Scenario Blueprint 的必要摘要、已观察到的 Frictions & Failure Modes、问题机制与 Priority Design Interventions；
    3. 优先场景、目标对象与目标动作；
    4. L1 Solution Archetype；
    5. 能力组合、服务触点以及交互/编排/自动化方向；
    6. 当前 horizon、后续 ambition horizons、排序假设与依赖；
    7. 行动边界、方案需求、基本可运营性要求；
    8. 设计假设、硬约束和交给 Integrated Assessment 的关键问题。

    1 Solution Hypothesis → 0..n Solution Outlines。若候选方案在 L1 Archetype、能力/交互形态或行动边界上存在实质差异，应分成独立 Outline Card；不在同一张 Card 中混写备选方案。

    6. 退出与后续交接¶

    可进入 Integrated Assessment¶

    当纲要能够清楚说明以下内容时，可作为综合评估的对象：

    • As-is 场景中的主要 Frictions / Failure Modes、问题机制与本轮 Priority Design Interventions 已得到足以形成主张的澄清；
    • To-be 场景的主要工作与服务机制变化已清楚，并能说明为谁、在什么优先场景中改善什么目标动作；
    • 方案采用什么 L1 Solution Archetype，以及能力、服务触点和行动边界如何配合；
    • 方案需要哪些信息、行动、责任、管控和基本可运营性条件；
    • 哪些设计假设、约束和关键问题需要验证。

    随后 Integrated Assessment 判断价值与战略适配、解决方案适配、技术可行性、推进准备度、风险与管控、投入与时机；它不重新替纲要定义方案内容。

    需要返回 Solution Hypothesis¶

    若比较发现差异已经改变受益对象、价值机制、初始范围或服务方向，而非仅改变方案形态、能力组合或行动边界，应返回 解决方案假设 — 形成，形成或修正不同 Hypothesis。

    7. 与后续活动的接口¶

    本活动输出 供后续使用方式
    L1 Solution Archetype、能力组合、服务触点与行动边界 作为解决方案适配、技术、风险与管控评估的对象；不等于评估结论
    信息与行动需求、基本可运营性要求 作为推进准备度评估的输入，判断前提是否具备、可在下一承诺前补齐或不可获得
    设计假设、硬约束与待验证问题 形成证据计划、技术验证、管控评估和投入/时机判断的输入
    多条 Solution Outlines 的比较 支持修正、保留或比较不同方案主张；不直接构成 Gate 结论

    接口边界：Solution Hypothesis 说明“可能以什么方向回应”；Solution Outline 说明“该方向需要是什么样”；Integrated Assessment 判断“这些主张是否有证据、条件与可接受性”；Decision Gate 才决定“是否、何时投入”。

    一句话¶

    解决方案纲要形成将一条 Solution Hypothesis 展开为可评估的方案主张：明确优先场景、L1 Solution Archetype、能力、服务触点、行动边界和所需条件，但不提前把证据、可行性、风险接受或投资结论写成方案事实。
