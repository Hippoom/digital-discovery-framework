    技术参与 Digital Discovery：问题与方法¶

    用途：定义解决方案架构师、技术负责人、数据/AI/平台专家如何参与 Digital Discovery 活动。Digital Discovery 不预设为 AI 或 Agent 方案。

    前置：Digital Discovery工作流 已将业务机会转为解决方案假设，并开始形成解决方案纲要。

    核心不是“尽早给出技术方案”，而是：为 Solution Outline、Integrated Assessment 与 Decision Gate 提供恰当粒度、可追溯的技术证据。

    关联：Digital Discovery v1、Reference/AI场景适配与能力边界。工程深化在获 Go 后进入相应建设路径；Agent-enabled 方向的专项工程实践不属于 Digital Discovery。

    1. 工作重点¶

    本阶段要解决的问题¶

    从技术视角参与 Digital Discovery 时，要回答哪些问题、以何种证据回答，并在何处止步交给工程？

    技术参与 Digital Discovery 的目标不是替代产品、业务、合规或工程团队，而是让每个决策关口不因技术不确定性而“拍脑袋”。

    不是 而是
    先选模型、向量库、Agent 框架 先证明问题适合哪类能力、是否需要 AI/Agent，以及为什么
    做一个看起来可用的 Demo 验证最可能推翻方案的关键假设
    给出确定的工期和报价 给出带假设、证据等级和不确定性的量级判断
    把所有工程细节提前设计完 定义进入相应建设路径前必须明确的决策、约束和验收方向；Agent-enabled 方向再进入 Harness

    2. 技术参与的职责边界：四类内容，不是一张“技术问题清单”¶

    技术人员不是所有字段的回答者。有些内容是业务 Context，有些是各方的共同鉴别，技术人员的核心职责是基于这些输入提出技术建议与证据，并共同设计验证和运营机制。

    Context（业务提供）
  → 共同鉴别（业务 / 产品 / 技术 / 管控）
    → 技术建议与证据（技术主责）
      → 可运营性判断（共同确认）
    类别 内容 主责 技术人员的角色
    Context 输入 谁在何情境下有何痛点；希望促成什么动作；业务价值与成功目标 投资方 / 业务 Owner / 产品 理解、追问和约束，不替业务定义价值
    共同鉴别 作用模式；问题类型组合；行动边界与确认人；数据/规则/系统/权限需要；运营责任与反馈机制 业务、产品、技术、管控共同 将业务语言技术化，暴露冲突、依赖和不可实现处
    技术建议与证据 能力组合；非 AI 替代方案；技术可行性、量级、风险；最高不确定性与验证路径 技术主责 给出带假设、证据等级和停止条件的建议
    可运营性判断 是否有 Owner、基本度量、更新与人工接管路径 业务/产品/技术共同 判断方案是否“接得住、改得动”；不在此设计完整运营体系

    技术人员真正需要主责回答的三个问题¶

    # 技术问题 回答什么 主要供数给
    1 基于已共同鉴别的问题，Outline 主张的能力组合是否存在可信技术路径？ Rules / Workflow / Knowledge Access / ML / Optimization / GenAI 各自承担什么；是否根本不需 AI；只有跨能力协调或受控交互必要时才采用 Agent；关键系统协作、信息读取与受控行动的技术条件是什么 Solution Outline 的技术评估输入
    2 该路径依赖哪些前提，哪些需要由 Assessment 判断？ 由问题类型和能力组合推导所需数据、知识、规则、约束、系统、接口与权限；技术缺口、依赖与核验结果作为输入，前提是否具备/可补齐由 Readiness to Proceed 判断，安全与风险接受由 Risk & Control 判断 Integrated Assessment 的 Technical Viability / Readiness to Proceed / Risk & Control 输入
    3 以何种最小证据判断技术条件是否支持进入 Inception？ 最小验证路径、技术可行性、成本/周期量级、关键质量技术条件、最小可运营性技术条件、停止/降级条件 综合评估记录卡 的 Technical Viability 结论与 Gate 条件

    Technology Assessment：两条工作流与 DFX 最小映射¶

    技术侧对相对稳定的 Solution Outline 并行形成两类证据：

    Technology Assessment
├─ Functional Technical Feasibility & Integration
└─ Cross-cutting Quality & Minimum Operability Conditions
    工作流 技术侧回答什么 DFX 最小对齐
    Functional Technical Feasibility & Integration 能力职责、系统协作、信息读取、状态、规则与受控行动是否存在可信技术路径和集成条件。 默认 Functional Viewpoint；由具体 Concern 按需使用 Information / Concurrency。
    Cross-cutting Quality & Minimum Operability Conditions 关键质量、工程与最小可运营性技术条件是否存在可信路径；哪些假设必须通过 E0–E4 验证。 由 Stakeholder Concern 选择 Perspective，并按需形成 Development / Deployment / Operational 等最小 View。

    DFX 的术语、按 Concern 选择规则及跨评估线归属见 DFX 在 Digital Discovery 中的最小映射。Operational 是 Viewpoint；Testability 与 Observability 是 Concern 或能力要求，不自动成为新的 Perspective。

    边界：技术侧不重写 Solution Outline 的能力、触点或行动边界；不裁定数据、知识、系统、权限、Owner 或运营前提是否具备（Readiness to Proceed 主责）；不裁定安全、隐私、合规、审计或责任风险是否可接受（Risk & Control 主责）。技术负责提供支撑 Technical Viability 的技术事实、限制、可实现性与验证证据。

    工作逻辑：依赖不是自由罗列，而是由问题推导¶

    业务 Context：目标动作 + 业务成功目标
  ↓
共同鉴别：问题类型 + 行动边界 + 作用模式
  ↓
技术建议：能力组合（含非 AI 替代方案）
  ↓
能力分解：每项能力所需的证据、数据、规则、系统、接口、权限
  ↓
前提核验：哪些已具备？哪些缺失？哪些需验证？
  ↓
技术结论：可行性、量级、风险、验证路径、停止/降级条件

    例如：

    “薪酬咨询中判断是否符合条件”
→ Knowledge / Evidence Inquiry + Assessment
→ Knowledge Access + Rules（必要时 Workflow）
→ 推导出：政策来源、客户事实、规则版本、查询接口、客户隔离、确认/升级路径

    “成功如何验证”与“如何评测/运营”不可混为一项¶

    层次 要回答什么 主责 示例
    业务结果 业务为什么值得做，成功带来什么结果 业务 / 投资方 转化率、处理周期、库存占用、服务水平
    任务质量 方案是否正确完成其承诺的具体任务 产品 / 业务 / 技术共同 推荐命中率、一次解决率、人工转接率
    技术质量 系统能力是否满足关键技术条件 技术主责 规则正确性、证据可追溯、工具成功率、延迟、权限拒绝；按需以 DFX Perspective 跨最小 View 检查
    运行与学习 是否存在未来可监测、更新、回归、人工接管与复盘的基本路径 共同负责 最小技术信号、更新与接管条件；Owner、运营准备与完整 SLA/告警机制不在此阶段设计

    因此：业务成功目标是 Context；Digital Discovery 只据任务/技术质量和运行机制判断可运营性。它们关联，但不重复。

    可运营性判断在 Digital Discovery 中具体指什么¶

    它不是 Digital Discovery 期间实际运行产品，也不是上线前就设计完整的运营体系；它只判断未来是否存在一条可信的“接得住、改得动、发现问题能处理”的基本路径：

    判断项 Digital Discovery 期只需确认
    Owner 是否存在业务/产品/技术 Owner，能在上线后承担结果、内容/规则或技术问题
    基本度量 是否能定义最基本的业务结果、任务质量和技术/风险信号，而非完整评测体系
    更新与接管 知识/规则/策略是否有更新路径；异常或高风险情形是否存在人工接管/停用路径
    关键缺口 若上述任一项缺失，是否应成为 Defer 或 No-go 的条件

    简言之：业务定义“成功长什么样”；Digital Discovery 只判断“是否有可能证明成功、上线后是否接得住”。完整验证、运行、SLA、告警和持续改进机制在 Go 后的 Inception、Implementation 与运营中深化。

    3. 全轴参与：技术问题在何处出现¶

    框架是全轴工作法；技术角色并非只在“工程实现”时出现。不同阶段的技术参与深度不同。

    全轴段 技术参与的重点 要形成的证据 / 产出 不应过早做的事
    投资 判断技术路线是否存在；识别量级、关键依赖、重大不确定性 技术可行性假设、成本/周期量级、关键风险 承诺精确预算、选定实现技术栈
    Solution Outline 形成（中枢） 共同鉴别并形成技术建议、前提、边界和可运营性判断 Solution Outline 的技术输入与技术评估对象 直接把方案写成详细架构设计
    Inception / 建设线 与 IT 共建；将获 Go 的 Outline 切片深化为可实现、可验证的工程设计 架构决策、验收方向、关键约束落地 重新讨论已确认的业务价值和问题定义
    运营准备 设计指标、评测、知识/规则更新、人工接管与支持机制 运营准备项、上线准入证据 把运营交给上线后“自然发生”
    持续运营 观察效果、成本、风险与使用行为；识别新问题和假设失效 运营指标、复盘、再 Discovery 触发 把上线视为终点

    4. 方法：渐进式证据，而不是一次性方案设计¶

    4.1 总流程¶

    0. 对齐当前要拍的板：投资 / 方案 / 放行？
   ↓
1. 接收并澄清 Context：目标动作、业务成功目标、范围与红线
   ↓
2. 共同鉴别：作用模式 → 问题类型 → 行动边界 / 确认人
   ↓
3. 技术建议：能力组合（含非 AI 替代方案）
   ↓
4. 从能力组合推导前提：数据/知识/规则/系统/接口/权限及可运营性条件
   ↓
5. 找出最高不确定性，以最小证据验证：资料、样本、Spike 或受控试点
   ↓
6. 共同判断可运营性：Owner、基本度量、更新与人工接管路径是否存在
   ↓
7. 形成带假设的技术结论：可行性、量级、风险、下一步与停止/降级条件

    4.2 证据等级¶

    不确定性越高、推翻方案的影响越大，所需证据等级越高；不是所有场景都需要 POC。

    等级 证据 适用 典型活动
    E0：假设 尚未验证的判断 早期机会讨论 明确假设与影响，不把猜测写成结论
    E1：访谈/资料证据 Owner 访谈、流程文档、系统说明、历史资料 初步框定 访谈、文档核对、系统地图梳理
    E2：样本核验 真实数据/知识/接口样本，或规则/流程样本 判断是否具备前提 数据剖析、权限核对、样本问答、接口试读
    E3：技术 Spike 对最高风险假设的最小实验 技术路径存在重大不确定性 验证召回、可用数据、算法效果、接口可达性、延迟量级
    E4：受控试点 真实用户、真实流程、可度量的有限运行 需要验证价值或运营闭环 灰度试用、人工确认、评测与反馈闭环

    Spike 的纪律：验证最可能推翻方案的假设，不是做“炫技 Demo”。

    5. 最小技术 Digital Discovery 分析卡¶

    这是一张调查工作底稿，用于技术调查、访谈、取证与协作，不是“技术把所有问题答完”的表，也不是与 综合评估记录卡 平行的正式决策记录。字段按 Context → 共同鉴别 → 技术建议/证据 → 可运营性判断的工作逻辑排列。

    记录关系：本卡可保存调查过程、候选证据、E0–E4、最高不确定性和最小验证活动；一旦形成需跨线使用的技术结论、条件、风险、交接或 Gate 输入，应汇入综合评估记录卡。综合评估记录卡是面向稳定 Solution Outline 版本的正式跨线判断记录。

    类别 字段 要写什么
    Context 业务目标与目标动作 服务对象、场景、痛点、希望促成的动作、业务结果目标、范围与红线
    共同鉴别 作用模式与问题类型 职能决策/一线赋能等作用模式；问题类型组合；输入→判断/计算→输出→动作
    共同鉴别 行动边界与责任 解释/建议/执行档位；确认人；禁止动作；异常与人工接管
    技术建议 能力组合与逻辑方案 主/辅能力、能力分工、非 AI 替代方案；仅在跨能力协调或受控交互必要时说明为何需要 Agent
    技术建议 推导出的前提与依赖 由能力组合推导的数据、知识、规则、约束、系统/API、权限、Owner；记录技术依赖、缺口与核验结果，并交由 Readiness to Proceed / Risk & Control 形成其主结论
    技术证据 可行性与验证计划 关联的 Outline 主张、Stakeholder Concern、选用的 Viewpoint / 最小 View / Perspective（如适用）、假设及 E0–E4 证据等级、最高不确定性、最小验证活动、成本/周期量级、停止/降级条件
    共同判断 最小可运营性技术条件与推进准备度交接 是否存在技术上可观测、可支持、可恢复、可人工接管/停用的基本路径；Owner、基本度量、更新与运营前提由 Readiness to Proceed 形成主结论；不设计完整运营机制
    技术结论 建议 Supports / Conditional / Blocked；进入下一步所需 Technical Viability 条件、Readiness to Proceed / Risk & Control / Inception 交接

    这张卡是技术视角的决策证据包，不是详细架构设计书。

    6. 与 Integrated Assessment 及建设路径的接口¶

    交付对象 技术参与提供什么
    Solution Outline 能力组合、非 AI 替代方案、方向性技术依赖、技术约束与最小可运营性技术条件；不替代业务/SA 对方案主张的定义。
    Integrated Assessment — Technical Viability Functional Technical Feasibility & Integration，以及 Cross-cutting Quality & Minimum Operability Conditions 的证据、结论、量级、验证与停止/降级条件。
    Integrated Assessment — Readiness to Proceed / Risk & Control 数据、知识、系统、权限、Owner、运营前提以及安全、合规、审计、责任相关的技术事实、限制、控制可实现性与交接输入；不替代其主结论。
    Decision Package / Gate 技术条件、关键依赖、证据等级、量级、阻塞项、Go 前条件和 Defer 重启条件。
    Inception / Agent Harness（仅 Agent-enabled） 获确认的方向性能力与边界、技术约束、待深化的架构/工程议题、验证证据与运营要求。

    7. 下一阶段的工作重点¶

    1. 用本方法选择 2–3 个真实或历史场景做回填，检验两条 Technology Assessment 工作流、最小技术分析卡与 综合评估记录卡 是否足够；
    2. 从回填中提炼“常见前提缺口”与“常见技术误判”，反哺 Reference/AI场景适配与能力边界；
    3. 检验 DFX 最小映射 是否能按 Concern 选择足够的 Viewpoint / View / Perspective，而不引入完整架构设计；
    4. 再决定是否需要把“技术分析卡”固化为模板，或拆分出成本/运营等专项 Reference。

    一句话¶

    技术参与 Digital Discovery 的职责，不是抢先设计系统；而是以渐进证据回答“技术路径是否存在、缺什么条件、关键质量与风险何在、是否有最小可运营性路径”，并明确 AI/Agent 是否必要，让 Solution Outline、Integrated Assessment 与 Gate 的判断可被理性地作出。
